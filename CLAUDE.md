# Polyant (Monorepo)

Open-source platform for building AI assistants with long-term memory, multi-channel support, and per-instance customization. TypeScript/Node.js (ESM). npm workspaces monorepo.

## Tech Stack

- **Monorepo**: npm workspaces (`packages/engine`, `packages/web`)
- **packages/engine** (AI runtime + management API):
  - Agent Framework: Vercel AI SDK v6 (`ai`, `@ai-sdk/openai`, `@ai-sdk/anthropic`)
  - HTTP Server: NestJS 11 (OpenAI-compatible API + Management REST API)
  - Encryption: AES-256-GCM (Node.js crypto) for skill env vars and instance secrets
  - Database: PostgreSQL 16 with Drizzle ORM + pgvector + Full-Text Search (tsvector)
  - Memory: Native LLM extraction + pgvector (cosine similarity) + PostgreSQL FTS
  - Channels: Telegram (grammY), Slack (@slack/bolt), WhatsApp (WAHA)
  - Tracing: LangSmith
  - Validation: Zod
  - **Architecture patterns**: see `.claude/skills/backend-architecture/SKILL.md` for full reference (functional pipeline + NestJS bridge, tier-based AI gateway, self-registering tools, domain-oriented modules)
- **packages/web** (admin panel):
  - Next.js 16 (App Router)
  - React 19
  - Tailwind CSS 4 (CSS-first config, no tailwind.config)
  - shadcn/ui (new-york style, source-owned components)
  - lucide-react (icons)
  - next-themes (light/dark mode, localStorage)
  - **Design system**: see `.claude/skills/frontend-design-system/SKILL.md` for full reference (inspired: black primary, white-dominant, accent-only color)

## Commands

All commands can be run from the monorepo root. They delegate to the appropriate workspace.

```bash
# Engine (AI runtime)
npm run dev              # Start engine with tsx watch
npm run dev:engine       # Same as above (explicit)
npm run build:engine     # Compile engine TypeScript
npm start                # Run engine from dist/

# Web (admin panel)
npm run dev:web          # Start Next.js dev server
npm run build:web        # Build Next.js for production

# All workspaces
npm run build            # Build all packages
npm run lint             # ESLint all packages
npm run typecheck        # TypeScript check all packages
npm test                 # Run all tests

# Database (engine)
npm run db:generate      # Generate Drizzle migrations
npm run db:migrate       # Apply migrations
npm run db:studio        # Drizzle Studio GUI

# Engine tests
npm run test:unit        # Unit tests only
npm run test:integration # Integration tests
npm run test:functional  # Functional tests

# Infrastructure
docker compose up -d     # Start postgres (pgvector), open-webui
```

### Per-workspace commands

You can also run commands directly in a workspace:

```bash
npm run dev -w @polyant/engine
npm run build -w @polyant/web
npm run typecheck -w @polyant/engine
```

## Instance Configuration (Database-First)

**All instance configuration is stored in PostgreSQL — NOT on the filesystem.**

| Config | DB Table | Notes |
|--------|----------|-------|
| Prompts (7 sections) | `instance_prompts` | Seeded from `instances/defaults.ts` on create; the old editable `08-datetime` section is gone — datetime injection is the per-instance `datetime_injection_enabled` flag |
| Skills (global catalog) | `skills` + `skill_versions` | CRUD via `/api/skills` |
| Skills (per-instance) | `instance_skills` | Enable/disable, version pinning, env vars |
| Tools (global catalog) | `tools` | Self-registered at boot from `*.tool.ts` |
| Tools (per-instance) | `instance_tools` | Auto-recomputed when skills change |
| Secrets | `instance_secrets` | AES-256-GCM encrypted |
| Channels | `instance_channels` | Telegram, Slack, WhatsApp config |
| Room config | `instance_room` | One-to-one with instance, prompt + outbound channel |
| Event sources | `event_sources` + `event_definitions` | Webhook-based, config AES-256-GCM encrypted |
| Event backlog | `event_backlog` | pending → processing → completed lifecycle |
| Activity log | `room_activity_log` | Auto-compacted: 7d daily → weekly → monthly |
| Hooks | `instance_hooks` | Lifecycle event → action (v1: run tool), template args, per-event ordering |

**IMPORTANT — DO NOT use filesystem for any agent configuration:**
- Prompts are read via `getPrompts(instanceId)` from `prompts.store.ts` (60s TTL cache)
- Skills are discovered via DB joins in `supervisor/prompt.ts` → `discoverSkills()`
- Tool enablement is resolved via `getEnabledToolNames()` from `instance-tools.store.ts`
- Knowledge documents live exclusively in PostgreSQL (`knowledge_documents` + `knowledge_chunks`)
- The `workspaces/` directory holds **only** per-conversation tool sandboxes (`workspaces/<id>/conversations/<convId>/`) used by `readFile` / `writeFile` / `gitCloneRepo`
- There is no `_template/` directory — new instances are seeded from DB defaults (`instances/defaults.ts`)

**When adding a new tool:** create a `*.tool.ts` file in `packages/engine/src/agents/tools/` that `export default defineTool({ name, description, parameters, execute })` from `@polyant-ai/plugin-sdk`. `parameters` is a **static** Zod schema (must not read `ctx`) that `defineTool` serializes to JSON Schema at module load; `execute(input, ctx)` holds the business logic. The loader (`loadAllTools()`) collects the default export at boot — no other files need to be modified. The `tools` DB table is synced automatically. (The legacy `registerTool({ create: (ctx) => ({ parameters, execute }) })` self-registering shape still works during the migration — the loader + `buildTool` dispatch on the presence of `inputSchema` — but new tools use `defineTool`.) See [docs/plugins.md](docs/plugins.md) and the `plugin-authoring` skill.

**`hubspotContact` supports custom properties:** the tool accepts a generic `customProperties: Record<string, string>` parameter for create/update (to write HubSpot custom properties like `evento`), and `filters` + `returnProperties` + `limit` + `after` for search (to query and paginate by custom property). The tool never hardcodes property names — instance-specific values (like an event name) live in the instance prompt, not in the tool code.

**`hubspotContact` search resolves owner names:** when a search result carries `hubspot_owner_id`, the tool enriches each contact with `owner_name` and `owner_email` so agents print "Mario Rossi" instead of the numeric id. The id is retained (backward-compatible). Resolution goes through the shared `resolveOwnerNames(apiKey, ownerIds)` helper in `hubspot-fetch.ts` — the reverse of `resolveOwnerIdFromEmail` — which reads `/crm/v3/owners` (paginated) into a `Map<id, {name, email}>` backed by a 1h TTL cache keyed per `apiKey:id`; repeated lookups within the TTL skip the network, and a search whose results carry no owner makes no Owners API call. Enrichment is best-effort: an Owners API failure leaves `hubspot_owner_id` intact and just omits the names. **Required token scope:** the HubSpot Private App / Service Key must include `crm.objects.owners.read`.

**`slackPostMessage` tool:** framework-first, generico (`packages/engine/src/agents/tools/slack-post-message.tool.ts`). Accetta `channel` (nome `#nome`, ID canale `C...` o ID utente `U...`) e `message`. Usa le credenziali del canale Slack configurato sull'istanza corrente via `channelManager.sendOutbound(instanceSlug, "slack", channel, message)` — lo Slack adapter risolve automaticamente gli ID utente aprendo un DM. Il canale di destinazione vive nel prompt dell'instance (no config extra). Il body del messaggio NON è loggato in audit (solo la lunghezza) per evitare leak di PII.

**When adding a new skill:** use the Management API (`POST /api/skills`) or create entries in the `skills` + `skill_versions` tables. Never create skill files on disk.

**When modifying prompts:** use the Management API (`PATCH /api/instances/:slug/prompts`) or update `instance_prompts` rows. Default prompt content for new instances is defined in `packages/engine/src/instances/defaults.ts`.

## Key Conventions

- **ESM only** (`"type": "module"` in package.json, `.js` extensions in imports)
- **npm workspaces**: always run `npm install` from the monorepo root. Use `-w <package>` to target a specific workspace
- **Single `.env` at monorepo root**: shared by engine and docker-compose. Engine finds it via `import.meta.url`-based path resolution (searches package root, then monorepo root)
- **Tier abstraction**: components request `fast | standard | heavy`, not specific models. Mapping in `packages/engine/src/ai-gateway/config.ts`
- **Model capability catalog**: `packages/engine/src/ai-gateway/model-catalog.ts` is the single source of truth for per-`(provider, model)` metadata — pricing (`input/output/cacheRead?/cacheWrite?`) + capabilities (`reasoning/reasoningAlwaysOn?/vision/temperature/cache`). Adding a model = ONE entry with every field filled in. The gates (`isThinkingCapable`, `modelSupportsVision`, `temperatureSupported`, `cacheSupported`, `isReasoningAlwaysOn`, `reasoningControlFor`) and `estimateCost*` are LOOKUPS into it. The per-provider regexes in `config.ts` (`*Fallback` fns) + `vision.ts`'s `visionCapableFallback` survive ONLY as a logged fallback for un-catalogued ids (Bedrock/Nebius drift) — `warnCatalogFallback` logs once per (gate, provider, model). `model-catalog.test.ts` guards catalog integrity + that catalogued rows still match the fallback heuristic. **Capability values are LIVE-VERIFIED against the provider APIs** (OpenAI/Anthropic/Bedrock probed directly; corrections applied — e.g. o3/gpt-5.6 `reasoningAlwaysOn`, Bedrock haiku/minimax `reasoning`, gpt-5.4/4.1 cache-read rates; Nebius left on console modality tags — its OpenAI-compatible endpoint is too permissive for accept/reject probing). **Reasoning control IS in the catalog now** (NO model-id regex in any provider file): the `reasoningControl` field (`"effort" | "budget" | "adaptive"`, present ⟺ `reasoning:true`) is the single source for how a model's thinking is driven — `adaptive` marks the newer Claude (Opus 4.7/4.8, Sonnet 5, Fable 5) that require `thinking.type:"adaptive"`+`effort` and REJECT the legacy `enabled`+`budgetTokens` shape (a 400 — this had broken extended thinking on those flagship models on Anthropic 1P AND Bedrock); `budget` = Claude 4.6-and-earlier + Bedrock MiniMax; `effort` = OpenAI/Nebius + Bedrock gpt-oss. The ai-gateway builds the per-model thinking payload from `reasoningControlFor(provider, model)`, and every provider now applies the per-instance `thinkingLevel` (OpenAI/Anthropic previously hardcoded it); the web Settings reasoning-level select shows for any thinking-capable model (was Nebius-only). The only surviving model-id regexes are the LOGGED catalog fallbacks in `config.ts` (`*Fallback`) + `vision.ts` — never a bare `if` in a provider. **Reasoning LEVELS are per-model** (`reasoningLevels`, present ⟺ `reasoning:true`, LIVE-VERIFIED — the provider APIs declare them): gpt-5.x accept `xhigh`, adaptive Claude accept `xhigh`+`max`, o3/gpt-oss/Nebius/budget are `low/medium/high` only. `reasoningLevelsFor` feeds the `/api/instances/models` payload (the web Settings picker renders exactly this set) and `resolveReasoningLevel` clamps a requested level to the model's set at the ai-gateway boundary (so a stale/out-of-range effort never 400s). The builders FORWARD the clamped level (only the budget path maps low/medium/high → token presets); the API accepts the full union and the gateway is the single clamp point
- **Fire-and-forget post-processing**: after each response, messages are saved, summary updated, and memories extracted asynchronously without blocking the user
- **Config via Zod**: all env vars parsed and validated in `packages/engine/src/config.ts`. Never read `process.env` directly elsewhere (documented exceptions: `DEFAULT_INSTANCE_ID`, `WORKSPACES_ROOT`, `LOG_LEVEL`). Altre letture intenzionali (filtri subprocess env, default params per testabilità, tool registry `requiredEnv` discovery) sono marcate con commento `// CONVENTION-EXCEPTION:` nel codice e devono restare circoscritte a quei pattern
- **Logging verbosity (`LOG_LEVEL`)**: the shared logger factory (`utils/create-logger.ts`) gates output by level (`debug | info | warn | error | silent`, default `info`) via the exported `shouldLog(level)`. `info` keeps the high-value pipeline skeleton (request, LLM token/latency, tool results, supervisor + response timing); `debug` adds verbose per-step tracing (LLM call lines, tool-call args, system-prompt **length only**, context load). The full system prompt is **never** logged — use the per-instance `debug_enabled` flag or `DEBUG_LLM_PAYLOAD` for full-payload inspection. `LOG_LEVEL` is read directly from `process.env` (CONVENTION-EXCEPTION) so the foundational logger never depends on the Zod `config` graph (which would invert layering and break partial `config`/`fs` test mocks). The file logger (`utils/file-logger.ts`) tees `console.*` to daily files and strips ANSI color codes so on-disk logs stay plain-text and grep-able. Tests run at `LOG_LEVEL=debug` (set in `test-setup.ts`)
- **Channel adapters are per-instance**: configs stored encrypted in DB, started/stopped dynamically via admin panel or API
- **Inbound message coordinator** (`packages/engine/src/channels/message-coordinator.ts`): fragmented bursts on WhatsApp/Telegram (user splits one thought across multiple quick messages) are collapsed into a single pipeline run per conversation via a cancel-and-restart model. First fragment arms a soft-debounce timer (`MESSAGE_SOFT_DEBOUNCE_MS`, default 2000ms) and a typing timer (`MESSAGE_TYPING_DELAY_MS`, default 1500ms). Additional fragments within the soft-debounce window reset both timers; when the pipeline fires it runs with an `AbortSignal`. A fragment arriving AFTER the pipeline has started aborts the in-flight run and re-arms the soft-debounce — up to `MESSAGE_MAX_RESTARTS` (default 3) consecutive cancel cycles, after which further fragments accumulate and are flushed in a follow-up run. On abort the in-flight fragments are restored to the head of the buffer (`restoreOnAbort`) so the next pipeline run ALWAYS contains every fragment still without a reply. Only `whatsapp` + `telegram` channels are routed through the coordinator — web/slack/room bypass. Fragment rows are NOT persisted separately: only the concatenated `user` message is saved, and only AFTER the pipeline succeeds (aborted runs leave no DB trace). Engine restart mid-buffer drops buffered fragments (acceptable trade-off)
- **WhatsApp typing indicator**: the `MessageCoordinator` schedules `sendTyping(channelId, messageSid)` on the WhatsApp adapter `MESSAGE_TYPING_DELAY_MS` ms after the first fragment of a burst (default 1500ms). The adapter calls Twilio's `/v2/Indicators/Typing.json` endpoint. The indicator shows the animated "typing…" dots for up to 25s (auto-expires on outbound delivery). As a documented side-effect, Twilio also marks the inbound message as read (double blue check). If a pipeline completes before the typing delay elapses, the call is never made. Failures are logged, not propagated
- **Pipeline cancellation**: `handleMessage(msg, signal?)` and `handleMessageStream(msg, signal?)` accept an optional `AbortSignal` propagated end-to-end (supervisor → `ai-gateway.chat`/`chatStream` → Vercel AI SDK `generateText`/`streamText`). The `MessageCoordinator` creates a fresh `AbortController` per pipeline run and aborts it when a new fragment arrives mid-flight. `runPipelinePost` and `afterResponse` are short-circuited on aborted signals: no trace record, no DB persistence of the user/assistant messages — cancelled pipelines leave zero side effects in DB. Tool HTTP fetches already in flight complete on the remote server but their results are ignored (accept-waste trade-off — documented risk on non-idempotent tools like `slackPostMessage`)
- **Conversation state store** (`packages/engine/src/conversations/state.store.ts` + `state.buffer.ts`): a per-conversation shared key/value blob (`conversation_state` table, `data` JSONB) that EVERY tool reads/writes via `ctx.state` (`get`/`set`/`getAll`/`delete`/`channel`). A `scope`/`scope_key` abstraction (today only `scope="conversation"`, `scope_key=conversationId`) leaves room for a future per-principal tier without a schema change. The **trusted channel identity** (phone / chat id / userName) is seeded server-side under the reserved `_channel` key every turn — read it via `ctx.state.channel` instead of trusting an LLM-supplied argument (injection-resistant). Writes are **deterministic, tool-code only — NEVER an LLM-facing `remember()` tool** — and **commit-on-success**: a per-run `ConversationStateBuffer` flushes in `runPipelinePost` AFTER the abort gate (Postgres per-key jsonb merge `||` / `- key`), so an aborted/cancelled run leaves no DB trace, exactly like messages/memory. Reads are buffer-first then DB (a tool sees its own writes + prior turns). Guards: JSON-serializable values, 64KB cap, audit logs key+type only (never the value — PII). Wired into the `deleteConversation`/`deleteInstance` cascades. Per-instance flag `state_in_prompt_enabled` (default OFF, toggle in the web Settings tab) renders a read-only state section into the supervisor prompt; default keeps state purely tool-to-tool. Buffer creation skips auto-tasks; the `_channel` seed skips synthetic channels (room/scheduled/agent). Distinct from `memory/` (semantic long-term pgvector) — this is structured, trusted, per-conversation working state
- **Conversation lifecycle hooks** (`packages/engine/src/hooks/`): per-instance, DB-configured (event → action) pairs run by `runHooks()` at four fixed pipeline points — `conversation_start` (first turn with empty persisted history — abort-safe vs the coordinator's cancel-and-restart), `message_received` (pre-LLM), `response_generated` (post-LLM, pre-flush), `response_sent` (end of pipeline post; semantics = "handed to channel", NOT delivered). Hooks are observe-only, ALL awaited (sequential, `position` order, per-hook timeout 1–30 s, default 10 s) and log-and-continue — a failing hook never blocks the reply. Action type is `function`: a **hook function** authored via `defineHook(...)` from `@polyant-ai/plugin-sdk` (v1.2.0+), default-exported from a `*.hook.ts` file and discovered at boot by `loadAllHooks()` into `getHookRegistry()` (parallel to the tool loader; plugin `hooksDir`, default `hooks/`). A hook function is NOT a tool — it is never LLM-invoked and never appears in the Tools catalog. Its `handler(ctx)` receives a purpose-fit `HookContext` (built in `hook-context.ts`): `event`, server-built `payload`, `conversation` (read-only `ConversationHistoryApi`), `state` (the conversation store, READ+WRITE — pre-event writes are visible to the supervisor the same turn and ride the commit-on-success flush), scoped `secrets`, `instance.{provider,model,flags}`, and `ai.chat(...)` (an LLM accessor bound to the instance's configured model via the ai-gateway). The handler returns `void` OR a typed control object — `{ halt?, replaceResponse?, regenerate?, injectContext? }` — mapped by `functionActionExecutor` onto the run. (The legacy `tool` action type + `{{path}}` arg-templating + the `HOOK_HALT_KEY` result-key convention were removed in the function cutover; migration `0060_remove_tool_hooks` deletes stale `action_type='tool'` rows.) Hooks bypass `instance_tools` enablement (deterministic admin config, like harness tools), skip only auto-tasks (the `scheduled`/`agent` synthetic channels now DO run the full hook lifecycle on the conversational path; `room`/webhook are supervise-direct and wire only the pre-LLM `message_received` hook in their engines), and audit outcome only (never rendered args — PII). Every execution is ALSO recorded fire-and-forget in `hook_executions` (slug-keyed telemetry, `hook_id` intentionally not a FK; dropped by the deleteConversation cascade, preserved on instance delete like other telemetry) INCLUDING rendered args + truncated result (same exposure class as message `steps`; the global audit log stays outcome-only), exposed via `GET /api/conversations/:id/hooks` and rendered as expandable pills (input/output on click, shared `HookExecutionPill` component) in the conversation-detail timeline (a `message_received` pill legitimately precedes its user message row — that row is persisted commit-on-success at end of turn). `runHooks()` also returns `HookExecutionSummary[]`, threaded onto `StreamOutgoingMessage` so the typed SSE endpoint emits live `hook-execution` events (pre hooks after stream open, post hooks before `done` — which therefore awaits the synchronous post phase); the playground renders them on the assistant turn. Extensible via `action_type` + executor registry in `hook-runner.ts`. Managed via `GET/POST/PATCH/DELETE /api/instances/:slug/hooks` + web "Hooks" tab. **Hook control return** (`HookResult`, `void` = observe-only): (1) `halt: { message, persist? }` — pre-LLM only (`message_received` everywhere, `conversation_start` on the conversational path): skips the LLM and delivers `message` as the assistant reply, persisted like an LLM turn; the runner stops at the first halt; wired via `runPipelinePre` → `shortCircuit` in `handleMessage`/`handleMessageStream` plus the supervise-direct Room + Webhook engines. `persist: false` (SDK v1.5.0+) makes the halted turn **ephemeral**: `runPipelinePost` skips the `pipeline_traces` row, BOTH `stateBuffer.flush()` calls, `afterResponse` (user/assistant rows, summary, memory, debug payload) and the contextPrompt clear — while still running `response_generated`/`response_sent` and writing the `hook_executions` row (the execution happened; only the turn didn't). Absent ⇒ persisted, as before. Honored on the conversational path only — Room/Webhook never call `runPipelinePost`, so they ignore it. (2) `replaceResponse: { message }` — `response_generated` only: replaces the LLM reply before delivery; honored only when the hook declares `mutatesResponse: true`, which makes the engine run that turn **non-streamed** (declare-and-buffer: `hasResponseMutatingHook` → `handleMessageStream` routes through the buffered `runBufferedTurn`), so the replacement is never too late; a `replaceResponse` without `mutatesResponse` on a streamed turn is warned, not silently dropped. (3) `injectContext: string` — pre-LLM only: appended as a system message to the turn's LLM input. (4) `regenerate: { reason? }` — `response_generated` only: discards the LLM output and REPLAYS the whole supervisor turn (system prompt + tools), driven by `generateWithReplay` in `hooks/response-replay.ts`. **HARD-gated on `mutatesResponse: true`** — because replay costs up to 6× a normal turn, an undeclared `regenerate` is DROPPED (warn), not honored, unlike `replaceResponse` (a cheap text swap still applied warn-only on non-streamed turns). The hook owns the stop condition via `payload.response.regenerationCount` (0 on the first pass); the engine only enforces a hard cap `MAX_REGENERATIONS = 5`. `regenerate` WINS over `replaceResponse` in a pass: a same-pass `replace` applies only on a pass where nobody asked to regenerate, and when the loop exits with `regenerate` still set (cap hit / aborted) the raw last output ships — never a superseded `replace`. Extracted seam: `runResponseGeneratedHooks` runs the post-LLM hooks in the loop (abort-safe — it skips the hooks entirely once the signal is aborted, since it now runs BEFORE `runPipelinePost`'s abort gate), then `runPipelinePost` is called with `responseGenerated` so it neither re-runs those hooks nor re-applies replace — one persisted turn. Spend (tokens/cost/latency) is SUMMED across all replay passes into the single `pipeline_traces` row via `addPassSpend` (each pass still logs to `ai_logs` independently); content fields (steps/tools/reasoning/model) are the delivered pass. Wired ONLY into the buffered conversational path (`runBufferedTurn`, which `mutatesResponse` already forces non-streamed); room/webhook run `response_generated` for `replaceResponse` but have no replay loop (they pass `regenerationCount: 0`). **CAVEAT: replay re-executes the whole turn, tools included** — a non-idempotent tool can fire up to 6× and the per-conversation `stateBuffer` accumulates writes across discarded passes, so enable a `regenerate` hook ONLY where the turn is side-effect-free or its tools are idempotent; deterministic (`temperature:0`) turns reproduce identical output and just burn the cap (regenerate suits sporadic output corruption, not systematic errors). Hook-authored replies (halt or replace) persist `metadata: { source: "hook", hookName }` on the assistant row (`hookProvenance`) so the web can badge them. The halt/replace/inject contract types live in `@polyant-ai/plugin-sdk` (`HookResult`/`HookContext`/`HookSpec`). A read-only catalog is at `GET /api/hook-functions`. **First-party hook functions** live in `packages/engine/src/hooks/functions/` (scanned by `getCoreHooksDir()`); the first one is **`conversation-reset`**: on a message that is exactly `RESET` (trimmed, case-insensitive, whole message — same deterministic-keyword shape as the GDPR opt-out gate) it renames the current conversation to `<conversationId>#<5 random digits>` via `conversationStore.renameConversation` (which moves messages, ai_logs, traces, audit, hook_executions, memories AND `conversation_state`), then halts with `persist: false`. Effect: the old conversation stays browsable in the panel under the suffixed id, the next inbound message re-creates the canonical id EMPTY, and the RESET exchange itself lands in neither. Purpose: a conversation id is `${slug}:${channel}:${channelId}`, so colleagues testing an agent from one WhatsApp number otherwise share one ever-growing conversation. Enable it per instance from the Hooks tab (test agents only — the keyword is hardcoded, not configurable). Caveat: the `MessageCoordinator` concatenates a fragment burst, so `RESET` followed immediately by more text arrives as one message and does NOT match. Design: `docs/superpowers/specs/2026-06-10-hook-system-design.md` + `docs/superpowers/specs/2026-07-02-hook-halt-and-respond-design.md` + `docs/superpowers/specs/2026-07-03-hook-functions-design.md` (the tool→function replacement; plan: `docs/superpowers/plans/2026-07-03-hook-functions-engine.md`) + `docs/superpowers/specs/2026-07-23-hook-regenerate-replay-design.md` (the `regenerate`/replay control return; plan: `docs/superpowers/plans/2026-07-23-hook-regenerate-replay.md`) + `docs/superpowers/specs/2026-07-29-conversation-reset-keyword-design.md` (`halt.persist` + the `conversation-reset` hook; plan: `docs/superpowers/plans/2026-07-29-conversation-reset-keyword.md`)
- **Tool-result replay (cross-turn)** (`packages/engine/src/conversations/tool-history.ts`): by default the model's cross-turn history is text-only (`getRecentMessages` selects `role`+`content`), so prior-turn `tool_use`/`tool_result` blocks are NOT replayed — a tool's output is invisible to the model on the next turn unless it was echoed into the reply text (the API is stateless; nothing is stored provider-side). Per-instance flag `tool_results_in_history_enabled` (default OFF, web Settings toggle) opts in: `preparePipeline` re-fetches the in-window rows and `buildHistoryWithToolResults()` reconstructs the assistant `tool-call` + `tool`/`tool-result` ModelMessages from the persisted `steps` (every call paired with a result — synthesized if missing; multi-step turns flattened to one parallel-call shape), truncated to `MAX_REPLAYED_RESULT_CHARS` (2000). Extra fetch ONLY when the flag is on — the default text path is untouched, and dropped messages/summary stay text. CAVEAT: the AI SDK v6 message shape is unit-tested but should be validated against a live provider before enabling in production. The dormant `ai-gateway/reasoning-injector.ts` (Anthropic signed-thinking re-injection) is a separate, currently-unwired mechanism — do not conflate
- **Per-turn debug capture** (`debug_enabled` flag): by default the exact LLM request is NOT persisted — only `role`/`content`/`steps`/`reasoning` survive on the message row, so the full system prompt, the messages array sent, and the tool definitions are discarded after the call (only LangSmith, if enabled, keeps them externally). Per-instance flag `debug_enabled` (default OFF, web Settings toggle) opts in: the gateway captures `{ system, messages, tools }` when `ChatRequest.captureDebug` is set (threaded pipeline → supervisor → gateway; tool params serialized best-effort via `zod-to-json-schema`, degrading to name+description), returns it on `ChatResponse.debugPayload`, and `afterResponse` persists it to `conversation_messages.debug_payload` (jsonb, nullable). It is NEVER selected by the default `getMessages` list query — fetched on-demand via `GET /api/conversations/:id/messages/:messageId/debug` (returns `{ debugPayload, steps }`, scoped by conversationId, messageId UUID-guarded). The web `DebugSheet` (shared by playground + conversation detail) renders it on click; the streaming handler pre-generates the assistant message UUID and the native `chat/stream` controller echoes `{ conversationId, messageId }` in the `done` SSE event so the playground addresses the persisted turn without ordinal-matching. Heavy + PII at rest — opt-in only; persisted behind the same abort/commit-on-success gate as messages, cascaded on delete. A separate `GET /api/conversations/:id/state` exposes the conversation state-store snapshot (read-only) for the web "Context store" panel
- **Native typed-SSE chat endpoint** (`POST /api/instances/:slug/chat/stream`, `instance-chat-stream.controller.ts`): the first-party endpoint the admin playground uses. Unlike `/v1/chat/completions` (OpenAI-compat, text-only with `<think>` markers), it emits a typed SSE stream (`step-start`/`step-finish`/`reasoning-delta`/`reasoning-signature`/`reasoning-redacted`/`tool-call`/`tool-result`/`text-delta`/`done`/`error`) mapped from the AI SDK v6 `fullStream`, exposing the full multi-step + reasoning timeline live. `@Public()` + per-instance API key auth (shared `validateInstanceApiKey` helper, same as `/v1`). Aborts the pipeline on client disconnect; `done` carries `{ conversationId, messageId }`
- **Per-instance config**: AI keys, LangSmith, auth, channels, and Tavily are stored per-instance in `instance_secrets`/`instance_channels` tables. Resolved at runtime via `config-resolver.ts` (30s TTL cache). Only infrastructure vars remain in `.env`/`config.ts`
- **Tool registry**: tools are authored as `export default defineTool(...)` (from `@polyant-ai/plugin-sdk`) in `*.tool.ts` files under `packages/engine/src/agents/tools/`. `defineTool` serializes the static Zod `parameters` to **JSON Schema at module load, in the tool's own realm** — the only things crossing the tool↔engine boundary are **data** (`inputSchema`) and a **function** (`execute(input, ctx)`), never a live Zod object or a shared singleton. The engine-owned loader (`loadAllTools()`) collects the default export into the registry Map (`registry.ts` is its only writer); `buildTool()` turns a definition into a Vercel AI SDK `Tool`. The supervisor queries `getToolRegistry()` — no hardcoded tool imports. Per-instance enablement stored in `instance_tools` table (auto-recomputed when skills change). Legacy path: `registerTool({ create })` (Zod-object self-registration) still loads (dispatch on `inputSchema`) so migration is incremental
- **Plugin system**: external git repos of `*.tool.ts` files authored against `@polyant-ai/plugin-sdk` (a stateless, versioned public contract — git dependency `git+https://github.com/polyant-ai/polyant-sdk.git#v1.0.0`, its own repo `github.com/polyant-ai/polyant-sdk`). The loader scans N roots unioned + de-duped by manifest `name`: `PLUGIN_DIRS` (comma-separated absolute paths, `config.plugins.dirs`, env wins de-dup) ∪ the convention dir `packages/engine/src/plugins/*` (gitignored runtime drop dir). Each root carries a `plugin.json` (`name`, `version`, `engine` semver range, `toolsDir` default `tools`, `namespace` default `name`); every tool loads as `<namespace>:<name>`. A plugin whose `engine` range excludes the running engine version is **skipped with a warning** (boot continues); duplicate final names fail the boot loudly. Discovery/naming/enablement flow through the same `loadAllTools()` → registry → `instance_tools` pipeline as core tools — no DB or API changes. **Module-resolution rule**: a plugin file resolves its imports from its **realpath**, so a plugin must be either a **real dir in-tree** (`src/plugins/<name>`, resolves the monorepo's `node_modules`, `tsx watch` hot-reloads) or an **out-of-tree dir with its OWN `node_modules`** (`npm install` there with the SDK as a git dep, point at it via `PLUGIN_DIRS`, no hot-reload). **Never a symlink** — `tsx` resolves the symlink's realpath (the external repo) and can't find the monorepo deps. The serialized-data boundary is exactly what lets the engine and each plugin resolve their **own** copies of the SDK/`zod`/`ai` without breakage. See [docs/plugins.md](docs/plugins.md), the `plugin-authoring` skill, and the design record at `docs/superpowers/specs/2026-07-02-serialized-plugin-mechanism.md`
- **Global skill library**: skills are stored in `skills` + `skill_versions` DB tables. `SkillsService` manages listing/CRUD via `/api/skills`. Per-instance assignments in `instance_skills` table
- **Sub-agent types**: `SubAgentDefinition` interface in `packages/engine/src/agents/sub-agents/types.ts`
- **Instance personalization**: prompts, skills, tool availability are stored in PostgreSQL (`instance_prompts`, `instance_skills`, `instance_tools`), NOT on the filesystem
- **Independent deployment**: each package under `packages/` is deployable as a standalone service
- **Framework-first, never instance-specific**: Polyant is a general-purpose framework for creating virtual assistants of any kind. Code changes (tools, prompt templates, supervisor logic, pipeline) MUST be domain-agnostic. Never hardcode instance-specific logic (e.g., sales workflows, medical terminology, specific tool orchestration patterns). Instance-specific behavior is configured entirely through per-instance data: prompts, skills, tool enablement, and secrets. If a behavioral issue is found in one instance, the fix must be a general-purpose mechanism that any instance can leverage
- **Room is event-driven, not conversational**: the Room scheduler processes pending events on a 30s tick, not on user messages. Each cycle creates a **new conversation** (`room:{instanceId}:{timestamp}`) — never persistent. Human replies on the outbound channel trigger an immediate cycle via `triggerImmediate()`
- **Event matching uses LLM tier "fast"**: sequential evaluation, first match wins. Definitions are priority-ordered
- **Harness tools bypass instance_tools**: tools with `harness: true` are not in the `instance_tools` table. They are injected by the engine when `includeHarness` matches their category (e.g. `"room"`). The supervisor's `buildTools` skips the enabledNames gate for harness tools. **On the inbound conversational path** `runBufferedTurn` passes `includeHarness = new Set([msg.channelType])`, so a harness tool whose `category` equals the inbound channel type is equipped generically (no allow-list) — today that is only `send_whatsapp_template` (category `"whatsapp"`) on a live WhatsApp chat; channels with no matching category are a no-op. `send_outbound_message` (category `conversation-trigger`) is deliberately NOT reachable this way — it still requires a webhook trigger context
- **Tool-delivered replies (`replyHandled`)**: a tool may deliver the reply itself (`send_whatsapp_template` sends an interactive Twilio Content template; `send_outbound_message` sends via the trigger channel) and signal `{ replyHandled: true, replyText }`. The pure helper `resolveDeliveredReply` (`packages/engine/src/reply-delivery.ts`) resolves the precedence — persist `replyText` (what the user actually saw), and return an EMPTY text so the channel adapter does not send a second bubble. Wired into `runBufferedTurn` (inbound path, mirroring the precedence the webhook engine already applied at its own send site). `send_whatsapp_template` resolves its outbound target from the webhook trigger context when present, else from the trusted server-seeded `ctx.state.channel` (never an LLM-supplied argument), which is what makes it usable inside the open 24h WhatsApp customer-service window. **Known gap (out of scope):** a `response_generated` hook `replaceResponse` on a turn where a tool already delivered its reply is unhandled — the replacement is persisted but the template is what shipped. Spec: `docs/superpowers/specs/2026-07-24-whatsapp-interactive-inbound-design.md`
- **Channel boot is fire-and-forget**: `channelManager.startAllForInstance()` is NOT awaited at boot — Slack socket mode can hang and block the entire startup sequence (schedulers, room scheduler). Errors are logged, not thrown
- **Title generation is shared**: `packages/engine/src/utils/title-generator.ts` provides `generateConversationTitle()` used by both the main pipeline (`index.ts`) and the room engine. Never duplicate the title prompt inline
- **GDPR opt-out (STOP/START)**: deterministic keyword gate runs at two chokepoints — a pre-LLM inbound gate at the top of `handleMessage`/`handleMessageStream` (short-circuits opted-out contacts; `runOptoutGate` in `packages/engine/src/optout/optout-gate.ts`) and outbound suppression inside `channelManager.sendOutbound`/`sendOutboundTemplate` (blocks proactive sends, coordinator bypasses with `skipOptoutCheck`). Opt-out state persisted per `(instanceId, channelType, channelId)` in `contact_optouts` table (cascade on instance delete, NOT on conversation delete). Config lives as six columns on `instances` (opt-out enabled, stop/resume keywords, closing/resuming messages, prompt-hint enabled). The LLM is never the enforcer; the keyword is injected into the supervisor prompt purely as informational context. Admin endpoints: `GET/POST/DELETE /api/instances/:slug/optouts`. v1 limitation: STOP as a reply to a Room broadcast is not honored. Spec: `docs/superpowers/specs/2026-06-11-gdpr-optout-design.md`
- **Management write-audit log** (`packages/engine/src/management-audit/`, RBAC Stream 7): destructive management-plane mutations (`agent.create`/`agent.delete`, `secret.write`/`secret.delete`, `member.remove`) leave a forensic row in `management_audit_logs` carrying actor (`actor_user_id` + `actor_email`, both nullable for gateway/edge identities) + target (`target_type` + free-form `target_id`, FK-free so rows survive target deletion) + action. Controllers obtain the actor via `@CurrentUser()` and call `createManagementAuditLogger().log({ action, actor, targetType, targetId })`; actions and target types are closed-set constants (`ManagementAuditAction` / `ManagementAuditTarget`) — never magic strings. The secret VALUE is never audited (key only). The buffered `ManagementAuditStore` (init/shutdown wired in `index.ts`, batch on 10 / flush 5s, re-buffer-on-failure capped) mirrors the AI-runtime `AuditStore`. **Distinct from** the EE `authz_audit_logs` (authorization read/access — has NO OSS write path, guarded by a regression test) and the AI-runtime `tool_audit_logs` (per-tool-call pipeline audit). `member.remove` constant exists ahead of its (later RBAC stream) OSS endpoint.

## Development Workflow

### Before starting important features

- Use `/brainstorming` to explore intent, requirements, and design before writing code
- For multi-step features, write an **openspec** (spec document) before implementation to align on scope and approach

### After completing a feature

- **Test coverage**: review existing tests — migrate or update tests broken by the changes, and write new tests for the added code. Aim for meaningful coverage, not just happy paths
- **Typecheck + lint**: run `npm run typecheck` and `npm run lint` before considering the feature done
- **DB migrations**: if Drizzle schema was modified, run `npm run db:generate` and review the generated migration before applying
- **Config sync**: if new env vars were added, ensure they are in `packages/engine/src/config.ts` (Zod schema) and documented in `.env` / `docker-compose.yml` as needed

### After completing a feature (knowledge capture)

- **Update CLAUDE.md**: evaluate if the feature introduced new conventions, caveats, or architectural decisions that should be documented here for future sessions

## Important Caveats

- **Embeddings are per-instance, with an INDEPENDENT embedder provider.** The embedder is a dedicated `instances.embedding_provider` column (`openai` | `bedrock`; Anthropic has no embeddings API), chosen **separately from the chat `provider`** — changing the chat LLM never touches embeddings (migration 0052 backfilled `embedding_provider` from the chat provider so existing instances were unaffected). Each instance also has `embedding_dim` (1024 or 1536): OpenAI can emit either, Bedrock Titan v2 is always 1024. `embeddingProviderFor(provider)` survives only as the default at instance creation and for the migration backfill — it is NOT the runtime source of truth. `provider-resolver.ts` resolves the embedder model + credentials from `embedding_provider` (an `openai` embedder needs `openai_api_key` even when chat is bedrock/anthropic; a `bedrock` embedder needs AWS creds even when chat is openai). The admin Settings tab exposes a dedicated **Embedder** select. The `memories` and `knowledge_chunks` tables have two parallel vector columns (`embedding vector(1536)`, `embedding_1024 vector(1024)`) with an XOR check constraint — exactly one is populated per row, decided by `embedding_dim`. `computeMemoryStatus` validates `embedding_provider`/`embedding_dim` compatibility (via `SUPPORTED_DIMS`): a stranded state like bedrock + 1536 reports `canEnable: false` rather than falsely healthy.
- **AI-provider AWS credentials have a dedicated secret namespace, decoupled from tools.** The AWS credentials used by AWS-backed AI services (Bedrock chat, Bedrock embedder, Amazon Transcribe STT) live under `aws_provider_access_key_id` / `aws_provider_secret_access_key` / `aws_provider_region` in `instance_secrets` (see `SECRET_KEYS`). These are intentionally **distinct** from the generic `aws_access_key_id` / `aws_secret_access_key` / `aws_region` keys that tools (e.g. `file-upload`/S3) declare as `requiredSecrets`, so the AI provider and a tool can point at different AWS accounts without sharing one slot. `config-resolver.ts` (chat `apiKeys.bedrock_*` + STT `sttCredentials.aws`), `embeddings-gateway/provider-resolver.ts`, and `memory-status.ts` all read the `aws_provider_*` keys; the region still falls back to `process.env.AWS_REGION` then default `us-east-1`, and to the AWS SDK default provider chain (ECS/EC2/SSO) when no explicit credentials are set. The bearer token `bedrock_api_key` is unchanged and still takes precedence over SigV4. The Settings-tab AWS card renders whenever chat, embedder, **or** STT uses AWS (one shared block). No migration exists — pre-existing instances re-enter these credentials once.
- **Changing the embedder provider is destructive — no conversion/migration.** Embeddings produced by different providers live in incompatible vector spaces, and re-embedding existing data is slow, costly, and error-prone. So switching an instance's `embedding_provider` (openai↔bedrock) does NOT convert existing vectors — it **wipes** them. `resetEmbeddingsForProviderSwitch(slug, uuid, newEmbeddingProvider)` (in `embeddings-gateway/embedding-reset.service.ts`) deletes ALL memories and the ENTIRE knowledge base (documents + chunks, raw content included) and realigns `embedding_dim` to the new provider's default, in one transaction. **The deletes are keyed by the instance SLUG** (the `memories`/`knowledge_*` `instance_id` columns store the slug, not the UUID); the `instances` row update is keyed by the UUID. Passing the UUID to the slug-keyed deletes was a bug that left data orphaned while only realigning the dim — the function now takes both identifiers, branded, so the compiler prevents recurrence. Conversations are untouched — only extracted memories are removed, so keyword (FTS) search over raw messages keeps working. The `PATCH /api/instances/:slug` handler detects the switch with `embeddingProviderChanged` (which now compares `embedding_provider`, not the chat provider) and **rejects it with 400 when there is data to lose unless the body carries `confirmWipe: true`** — protecting scripted Management-API callers from silent data loss. The admin UI shows a destructive-confirmation dialog and sends `confirmWipe` after the user accepts; the PATCH response carries the `wiped` counts. The KB raw text survives a switch via **export/import** (below): export before switching, then re-import to re-embed at the new dim. Memories are not recoverable this way (they are LLM-extracted).
- **Knowledge-base export/import (JSON).** `GET /api/instances/:slug/knowledge/export` returns a JSON bundle `{ version, instanceSlug, documents: [{ filename, content, … }] }` (every document with its raw content). `POST /api/instances/:slug/knowledge/import` bulk-creates documents from such a bundle and re-embeds each with the instance's CURRENT embedder. Filename collisions are resolved by appending a progressive suffix (`manuale.txt` → `manuale (1).txt`), never overwriting; the bundle is validated up front (size, non-empty, per-instance cap) so the import is all-or-nothing, and the embedder must be configured before any document is created. The `export` route is declared BEFORE `:docId` so it is not captured as a document id. Web Knowledge tab has Export/Import buttons.
- **Instance (agent) export/import (JSON bundle).** `GET /api/instances/:slug/export` returns a full-config bundle (`export.service.ts` → `export.schema.ts`, envelope `{ version, exportedAt, type: "instance", instance }`); `POST /api/instances/import` (new) and `POST /api/instances/:slug/import` (overwrite) re-create/replace an instance from one (`import.service.ts`). **Format version is `1.1`** — the importer accepts both `"1.0"` and `"1.1"`; every field added after 1.0 is Zod-`.default()`ed so legacy 1.0 bundles still validate. The bundle covers: core metadata + ALL behaviour flags (`memory/knowledge/langsmith/auth/thinking/stateInPrompt/toolResultsInHistory/debug` + `langsmithProject` + `sttProvider`), GDPR opt-out config (six columns), `embeddingProvider`/`embeddingDim`, prompts, skill assignments (with pinned version), manual tools, channels, skill-env, **hooks**, room, event sources + definitions (incl. `action`/`contextPrompt`/`outbound*`), and scheduled tasks. **Secrets are NEVER exported** — only key names (→ `secret_required` warnings); encrypted skill-env values are omitted; **channel config is exported with credential-like keys stripped** (`stripSensitiveKeys`, pattern `/(?:token|secret|password|key|credential)/i`). On import a channel is (re)enabled ONLY if its non-secret config alone passes the channel's Zod schema — so the credential-less `agent` channel round-trips enabled, while telegram/slack/whatsapp import disabled + a `channel_credentials` warning. **`embeddingProvider`/`embeddingDim` are applied on import-NEW only**; import-OVERWRITE leaves them untouched (switching an existing instance's embedder is destructive — gated behind `confirmWipe` on PATCH, out of scope for import). Slug conflicts on import-new auto-rename (`-imported`, `-imported-2`, …). The web Instances page has Export (per-instance) + Import buttons; the bundle is opaque to the frontend (no client-side schema), so format changes need no web change.
- **AI SDK v6 shape is isolated at the ai-gateway boundary** — the v6→internal mapping lives in `ai-gateway/providers/base.ts`: `normalizeSdkSteps()` maps `toolCall.input`→`args`, `toolResult.output`→`result`, `step.reasoning`→`reasoningDetails`; `mapUsage()` maps `inputTokens`/`outputTokens` (from `result.totalUsage`) → `promptTokens`/`completionTokens`. The internal types (`SdkStep`, `TokenUsage`, `StepDetail`) stay stable, so the rest of the codebase is untouched by the major bump. Other v6 renames already applied: multi-step uses `stopWhen: stepCountIs(n)` (was v4 `maxSteps`); tools declare `inputSchema` (was `parameters`); messages are typed `ModelMessage` (was `CoreMessage`); OpenAI non-strict JSON Schema is forced via `providerOptions.openai.strictJsonSchema=false` in `resolveCallConfig` (replaces the removed `createOpenAI({ compatibility })` / `structuredOutputs`)
- **Prompt caching + cache-aware cost tracking** — the supervisor prompt is split so provider prompt-caching is effective. `buildSupervisorSystemPrompt()` returns `{ system, turnContext }`: `system` is the STABLE prefix (per-instance DB sections 1–7 + a framework note on the injected-context tags + the instance-static opt-out hint + any persisted webhook `contextPrompt`), `turnContext` is the PER-TURN volatile block (current datetime — gated by the per-instance `datetime_injection_enabled` flag — channel identity, running summary, conversation state), each piece wrapped in a semantic tag (`<current_datetime>`/`<channel_identity>`/`<conversation_summary>`/`<conversation_state>`). The supervisor injects `turnContext` at the **tail of the messages**: `buildUserContent` splits the current turn into SEPARATE content blocks — user words FIRST, attachments next, the volatile `<context>…</context>` block LAST — so the volatile tail never invalidates the cached system/history prefix and the model can tell its own words from injected context. (An empty user-words block is omitted: an uncaptioned image arrives as `message===""` and a leading empty text block is rejected by Anthropic/Bedrock.) Previously the minute-granular datetime lived in `system` and broke caching on every minute boundary. The skills query is `.orderBy(skills.slug)` **and** the core/plugin tool loader (`registry.ts` → `importRoot`) `.sort()`s the `readdirSync` file list, so BOTH the skills list and the tool order (tools sit at position 0 of the cached prefix, before system) are byte-stable across OSes/restarts/pods and never silently bust the cache. Cache breakpoints are injected via a `prepareMessages` hook on `createProvider`; the placement algorithm (move the folded `system` into a leading `role:"system"` message carrying the breakpoint = caches tools+system, plus a breakpoint on the last history message from the 2nd turn onward) is shared in `providers/prompt-caching.ts` (`injectCacheBreakpoints` + `withProviderCacheMarker`) and each provider supplies its own marker: **Anthropic** `providerOptions.anthropic.cacheControl = { type: "ephemeral", ttl: "1h" }` (`applyAnthropicPromptCaching`) — 1h, NOT the 5m default, because slow async channels (WhatsApp/Telegram) space turns minutes-to-sub-hour apart, so a 5m prefix would expire between turns and re-pay the write (2×) with no read; **Bedrock** `providerOptions.bedrock.cachePoint = { type: "default" }` (`applyBedrockPromptCaching`, 5m — the AI SDK exposes no 1h cachePoint), gated to cache-capable model families (`/anthropic|nova/` — a cachePoint on other Bedrock models is rejected with a ValidationException). The `prepareMessages` hook now receives `modelId` so a provider can gate on the concrete model. **Within a multi-step turn** a second, MOVING breakpoint is added via the AI SDK `prepareStep` hook (`ProviderHooks.stepMarker` → `makeStepMarker` in `prompt-caching.ts`): it marks the LAST message from step 1 onward, so accumulating `tool_use`/`tool_result` blocks are cached incrementally (step N reads the whole prefix step N−1 wrote, writes only the increment) instead of re-sent full-price on every step. It SKIPS step 0 (the initial user turn carries the volatile `<context>` tail, and single-step turns must not pay a wasted write) — so it is independent of where the volatile block sits — and is ADDITIVE to the one-shot breakpoints (system + history stay). `anthropicStepMarker` / `bedrockStepMarker` (cachePoint, gated identically to the one-shot marker) reuse the provider markers via the shared `markAnthropic`/`markBedrock` closures, EXCEPT the Anthropic within-turn marker uses the DEFAULT 5m TTL (not the 1h cross-turn TTL): within a turn steps are seconds apart so 5m suffices at a 1.25× write vs 1h's 2×, and it lands on the LAST message — after the 1h system/history breakpoints — satisfying Anthropic's rule that longer-TTL breakpoints appear first. `base.ts` builds the SDK `prepareStep` via a shared `buildPrepareStep` helper. OpenAI/Nebius supply no `stepMarker` so their calls are byte-identical. Validated live on Anthropic: over a 5-step tool loop the 4-breakpoint cap held (the SDK re-derives the base each step, so per-step marks never accumulate) and cache reads grew by exactly the prior step's writes. OpenAI caches automatically (no params). Cost/usage: the AI SDK v6 `inputTokenDetails.{cacheReadTokens,cacheWriteTokens}` breakdown is extracted in `mapUsage`/`buildUsage` into `TokenUsage.{cachedInputTokens,cacheCreationInputTokens}` (subset of `promptTokens`); `estimateCost` re-prices cache reads at a reduced rate and Anthropic cache writes at a premium via **absolute per-model cache rates** in the catalog (`costPerMillionTokens[m].cacheRead`/`cacheWrite` — published $/1M, NOT multipliers; `resolveCacheRates` falls back to the full input rate when a rate is absent, so a provider that reports cached tokens without discounting them — Nebius — is billed full, and non-cacheable families need no entry). Effective rates: anthropic read 0.1× / write 2× input (1h cross-turn); bedrock read 0.1× / write 1.25× (5m); openai pre-5.6 read 0.5× / no write premium; **gpt-5.6 (Sol/Terra/Luna) read 0.1× / write 1.25×** (`cache_write_tokens`). OpenAI caching is automatic + non-disableable. Bedrock cross-Region inference profiles (`us.*`/`eu.*`/`apac.*`/`global.*`) are priced at the base source-Region rate — no surcharge is modeled. `ai_logs` gained `cached_input_tokens` + `cache_creation_input_tokens` (migration 0063). Analytics surfaces the breakdown: the overview aggregates cache reads/writes → a **Cache hit rate** KPI card, and the conversation list + detail show per-conversation cache read/write. **LangSmith** already receives the cache token COUNTS automatically via the `wrapAISDK` middleware (no wiring needed; cache-adjusted USD stays in `ai_logs` because LangSmith auto-pricing is deliberately suppressed). **Caveat**: Anthropic/Bedrock caching has a write PREMIUM (Anthropic 1h = 2×, Bedrock 5m = 1.25×), so it is a NET LOSS when a written prefix is not re-read within the TTL — i.e. LOW-traffic instances with single-turn conversations on those providers. Two amortizers keep the default a win for the target workload: the system prefix is shared across ALL of an instance's conversations, and within-turn caching is re-read seconds later — so busy / multi-turn / agentic instances profit. **Per-agent cache control** (`cache_enabled` + `cache_ttl` columns, migration 0068, default on/1h = prior behaviour): the Settings tab exposes an on/off switch + a 5m/1h TTL select, threaded into `InstanceConfig.cacheConfig` → `ChatRequest.cacheConfig`. `enabled:false` skips ALL markers (`base.ts` gates BOTH `prepareMessages` and `prepareStep`) so the instance pays no cache write; `ttl` drives the Anthropic cross-turn breakpoint (the within-turn step marker stays 5m). It only meaningfully gates **Anthropic/Bedrock** (where we inject the marker): OpenAI caches automatically and the UI shows the switch locked-on; **Nebius caches automatically** — verified live it reports `cacheReadTokens` (implicit KV cache, like OpenAI) — but passes NO cost discount (open feature request), so cached tokens bill at the FULL input rate (`cacheSupported()` = false meaning "no discount"; `resolveCacheRates` leaves its rate = input, which is correct); it needs no marker, so the Settings switch shows locked-on (automatic). Bedrock TTL is 5m-fixed. The model picker surfaces per-model cache read/write $ ("—" where unsupported). Validate the exact SDK usage semantics live before trusting the dashboard.
- **Nebius Token Factory is an OpenAI-compatible chat provider** (`ai-gateway/providers/nebius.ts`, `provider="nebius"`). No bespoke adapter: it wraps `@ai-sdk/openai-compatible`'s `createOpenAICompatible({ baseURL: "https://api.tokenfactory.nebius.com/v1", apiKey, includeUsage: true })` inside the shared `createProvider`. Per-instance key is the `nebius_api_key` secret (`SECRET_KEYS.NEBIUS_API_KEY` → `config-resolver` `apiKeys.nebius` → `ChatRequest.apiKeys.nebius`). Reasoning models emit `reasoning_content`, which `@ai-sdk/openai-compatible` maps to reasoning blocks automatically. **Thinking is driven explicitly in `resolveCallConfig`** because Qwen3.5-family hybrid models reason BY DEFAULT: on a thinking-capable Nebius model (gate: `isThinkingCapable`), the gateway injects `providerOptions.nebius.reasoningEffort` when `thinking` is ON, and `providerOptions.nebius.chat_template_kwargs = { enable_thinking: false }` when OFF. `reasoning_effort` alone only tunes intensity — it does NOT disable reasoning; the vLLM chat-template kwarg is the real off-switch, forwarded verbatim into the request body by `@ai-sdk/openai-compatible`. The `providerConfigs.nebius` catalog in `config.ts` mirrors the account's live `GET /v1/models` (there is NO pricing/capability API — prices come from the console prices page, capability from the console modality tag, NOT the model name: e.g. `Nemotron-3-Nano-Omni` is text-only, `Cosmos3-Super-Reasoner`/`Kimi-K2.6` are vision). Reasoning gate: the `nebius` case in `isThinkingCapable`; vision gate: `VISION_CAPABLE` in `vision.ts`. **Version pin (build-breaking):** use `@ai-sdk/openai-compatible@^2.0.56` — it depends on `@ai-sdk/provider@3.x` (spec `LanguageModelV2/V3`), matching the repo's `ai@6`. The `3.0.x` line depends on `@ai-sdk/provider@4` (`LanguageModelV4`) and fails typecheck (`"v4" not assignable to "v2"`). Re-align this pin whenever `ai` is bumped.
- **Memory extraction is conditional** on the instance's `memoryEnabled` flag. The extraction prompt includes today's date and converts relative dates to absolute. Facts are written in the same language as the conversation.
- **No specialized sub-agents** — `spawnTask` creates ad-hoc agents; the `SubAgentDefinition` type exists for future extensions
- **Hybrid search uses RRF** (Reciprocal Rank Fusion) to merge pgvector cosine similarity results with PostgreSQL FTS keyword results
- **PostgreSQL FTS uses `simple` config** (no language-specific stopwords) to support multilingual content
- **Memory extraction** runs fire-and-forget after each response: the LLM extracts facts as structured JSON (content, category, importance), which are embedded and upserted into the `memories` table with cosine-similarity deduplication (threshold 0.90)
- **tsx and NestJS DI**: `tsx` (esbuild-based) does NOT support `emitDecoratorMetadata`. All NestJS constructor injection MUST use explicit `@Inject(ClassName)` — implicit type-based injection silently resolves to `undefined`. This is enforced by the custom ESLint rule `polyant/require-inject-in-nest-classes` (`packages/engine/eslint-rules/`): it flags any constructor parameter in an `@Injectable`/`@Controller`/`@Catch` class that lacks an `@Inject(...)` decorator. Plain classes instantiated with `new` (e.g. the channel adapters) are intentionally ignored
- **drizzle-kit with ESM**: `drizzle-kit generate` (run via the bare CLI, e.g. `npx drizzle-kit generate`) fails in this repo because of an ESM resolution issue. The `npm run db:generate` script wraps the workaround (`tsx ../../node_modules/drizzle-kit/bin.cjs generate`) so contributors can just run `npm run db:generate -w @polyant/engine` — invoking the CLI directly remains broken. No snapshot files exist, so `generate` always produces full-schema migrations — write incremental migrations manually
- **Next.js env loading**: Next.js only loads `.env` from its own package directory (`packages/web/`), NOT from the monorepo root. Auth vars (`AUTH_SECRET`, `DATABASE_URL`, `GOOGLE_*`) must be in `packages/web/.env.local` or duplicated
- **Next 16 conventions**: the auth middleware is `packages/web/src/proxy.ts` (Next 16 renamed `middleware.ts`→`proxy.ts`; the matcher still excludes `api`/`_next`/static so proxied API + `/v1` routes are NOT gated by the web session). Web lint runs as `eslint .` (the `lint` script) against native flat config (`eslint-config-next/core-web-vitals` + `/typescript`) — `next lint` was removed in 16; the newly-tightened react-compiler rules are currently kept at `"warn"` pending a dedicated follow-up. The root `package.json` `overrides.next` MUST track the installed Next major, or next-auth pulls in a second `next` copy. Auth.js route handlers are wrapped as plain `GET`/`POST(req: NextRequest)` in `app/api/auth/[...nextauth]/route.ts` because Next 16 type-checks handlers against `RouteHandlerConfig` (dynamic `params` is now a `Promise`)
- **Pipeline latency tracing** records per-phase timing for every user message (context prep, tool building, LLM call, total). Data is written fire-and-forget to `pipeline_traces` via a buffered `TraceStore` (flush every 10 entries or 5s). Tool call durations and streaming TTFB are also captured. Auto-tasks (Open WebUI title/summary) are excluded via `isAutoTask()` guard. The `ai_logs` table tracks individual LLM calls; `pipeline_traces` tracks end-to-end pipeline latency — they serve different purposes
- **Room scheduler is a singleton** (`roomScheduler`) with per-room mutex via a `running` Set. Multiple rooms process in parallel, but the same room never runs concurrently. The tick uses a batch query (`countPendingByInstance`) to avoid N+1
- **Webhook receiver always returns 200 OK** — processing is fire-and-forget. Events are dropped (not queued) if backlog cap (100) is reached. Payloads are limited to 64KB
- **Event source operations are instance-scoped**: all event source and definition mutations verify ownership via `instanceId` — event sources directly in the WHERE clause, definitions via `verifyEventSourceOwnership()` which confirms the parent event source belongs to the instance. The `mark_events_completed` harness tool also scopes by `instanceId`. This prevents IDOR across instances
- **`gitCloneRepo` credential lifecycle (#87)**: the GitHub token and the credential helper are written to `.git/polyant-token` (mode 0600) and `.git/polyant-askpass.sh` (mode 0700) inside each cloned workspace so that subsequent git operations (push/fetch by Claude Code) can authenticate. Both files are removed automatically by `cleanupRepo()` when the conversation ends and by `cleanupStaleRepos()` (stale threshold: 2h). **Trade-off**: while the workspace exists, the token is at rest on disk. Workspaces must be treated as ephemeral sandbox state: never backup/rsync/tar/commit them, never expose `workspaces/<instanceId>/` via any external share. A warning is logged if a leftover `.git/polyant-token` is detected during stale cleanup — that signals a crashed prior run

## Authentication & Authorization

### Current (Phase 1)

- **Frontend**: Auth.js v5 with Google OAuth; optional per-org sign-in domain allowlist. OSS path is one domain/org via `AUTH_ALLOWED_DOMAIN` (legacy comma-separated `AUTH_ALLOWED_DOMAINS` still honoured + merged; empty = allow all). The check lives in the **Node `signIn` callback in `lib/auth.ts`** (not the Edge `auth.config.ts`), backed by the pure helper `lib/auth-domain-allowlist.ts` (exact case-insensitive domain match — look-alike suffixes/prefixes are rejected). No domain is hardcoded; every tenant is env-configured. EE layers a per-org table + UI on top (out of OSS scope)
- **Session strategy**: JWT (encrypted JWE with A256CBC-HS512). Chosen because Next.js middleware runs in Edge Runtime which cannot make TCP/DB connections
- **JWT validation (engine)**: `auth-user.service.ts` decrypts Auth.js JWE using `jose` + `@panva/hkdf` with `AUTH_SECRET`. No DB query per request
- **Engine guard**: Global NestJS `AuthGuard` (registered via `APP_GUARD`). Reads JWT from `Authorization: Bearer <token>` header OR `authjs.session-token` cookie. Uses `@Inject(Reflector)` explicitly (tsx doesn't support `emitDecoratorMetadata`)
- **Public routes**: Decorated with `@Public()` — `/health`, `/v1/*` (the OpenAI-compatible API)
- **Completion API auth**: `/v1/chat/completions` uses per-instance API keys (existing mechanism: `instance_secrets` + `authEnabled` flag). NOT session-based
- **Frontend proxy**: Next.js rewrites proxy `/api/*` and `/memories/*` to the engine, forwarding cookies (JWT included)
- **DrizzleAdapter**: configured with custom schema mapping in `packages/web/src/lib/auth.ts` (snake_case DB columns, pluralized table names matching engine schema)
- **JWT trade-offs**: no immediate session revocation (valid until 30d expiry); user data frozen in token; `AUTH_SECRET` is single point of failure. If revocation needed later: short-lived JWT (15min) + refresh rotation is recommended path

### Gateway-authenticated mode (`AUTH_MODE=<gateway>`)

When the engine runs behind a cloud-managed auth gateway (ALB OIDC on AWS, GCP IAP, Cloudflare Access, Azure Easy Auth — future), set `AUTH_MODE` to the gateway name (currently only `alb-oidc` is implemented). `auth.guard.ts` dispatches on this value: in gateway mode it reads the identity header set by the gateway (`x-amzn-oidc-data` for ALB OIDC) via a per-gateway parser (`alb-oidc.service.ts`) instead of validating an Auth.js session. The header's JWT signature is NOT verified; the engine relies on network isolation (ECS security group accepts ingress only from the ALB SG) — this is documented in [ADR-0001](docs/adr/0001-gateway-authenticated-mode.md) along with the trust trade-offs and the deferred follow-up for signature verification. In this mode the `packages/web` container does NOT need `AUTH_SECRET`/`POSTGRES_*`/`GOOGLE_*` — Auth.js Edge middleware finds no `authjs.session-token` cookie (the gateway uses its own cookie), returns null without decrypting, and the engine becomes the sole source of authenticated identity. When adding a new gateway, add a new parser file under `packages/engine/src/auth/` and a new `AUTH_MODE` value; do NOT branch on cloud-specific logic inside `auth.guard.ts`.

**Gateway mode carries no tenancy, and is therefore currently UNUSABLE.** `parseAlbOidcData` cannot resolve `orgId` (there is no local `users` row to map the Cognito `sub` onto), so a gateway-forwarded principal has neither an org claim nor any `role_bindings`. Since RBAC is enforced unconditionally and there is no longer an `AUTHZ_ENFORCE` escape hatch, such a principal resolves no scope and is **denied on every `@RequirePermission` route**, and `TenantService` answers `organization: null` so the panel renders the tenant-unavailable state. That is not a bug to patch at the guard or in `TenantService` — the missing piece is the gateway-identity → local-user mapping. **Do not deploy `AUTH_MODE=alb-oidc` until it exists**; use `AUTH_MODE=session`.

### Multi-tenancy & RBAC (implemented — migration 0051)

Hierarchy: **Organization > Workspace > Agent** (the agent table is still named `instances`). The "Project" level of the original design was renamed **Workspace**; there is no `projects` table.

- **Tables**: `organizations`, `workspaces`, `organization_memberships` (`organizations/organization.schema.ts`); `roles`, `role_permissions`, `role_bindings`, `authz_audit_logs` (`authz/*.schema.ts`). `instances.workspace_id` is a `NOT NULL` FK (`onDelete: restrict`)
- **Single-tenant in practice, multi-tenant in schema**: migration 0051 seeds exactly one organization + one workspace (`is_default = true`), and `instances/store.ts` always resolves `findDefaultWorkspaceId()` on create. There is **no org/workspace CRUD** (neither API nor UI) — the workspace level is invisible to the user today, but adding organizations later needs no migration
- **Roles**: four seeded system roles — `owner` (level 40), `admin` (30), `member` (20), `viewer` (10) — with `organization_id NULL` + `is_system = true`. The `resource:action` permission taxonomy and the exact role matrix live in `authz/permissions.ts`, the single source of truth shared by the migration seed and the tests. Never inline a permission string. Custom per-org roles are EE
- **Bindings**: `role_bindings.scope_type` is `organization | workspace` and `scope_id` is polymorphic, so it carries no declarative FK — integrity comes from the `check_role_binding_scope` trigger. Resolution is **most-specific-wins** (`authz/authorization-strategy.ts`): a workspace-scoped binding is authoritative and both *grants* permissions the org binding lacks AND *revokes* ones it grants; no applicable binding → deny
- **Guard**: `PermissionGuard` is `APP_GUARD` #3 (after `ThrottlerGuard`, after `AuthGuard`), driven by `@RequirePermission()`. **RBAC IS ENFORCED UNCONDITIONALLY — there is no shadow mode and no `AUTHZ_ENFORCE` flag.** Every denial is a 403, including on routes that declare no permission. The flag used to exist and defaulted to shadow (deny → log → allow) while the decorate-all sweep was in flight; `.env.example` shipped `AUTHZ_ENFORCE=false`, so installs that copied the sample ran with every `@RequirePermission` reduced to a no-op and cross-org isolation off. It was deleted rather than re-defaulted: a switch that turns authorization off is not worth keeping. **Three declarations satisfy the guard**, and `route-authorization-guardrail.test.ts` accepts exactly the same three (keep the two in lockstep; the test DERIVES the controller list from the NestJS module graph — it used to walk a hand-maintained `ALL_CONTROLLERS` array that had drifted and hid seven handlers that 403 under enforcement): `@RequirePermission()` (RBAC), `@RequireRole()` (deployment-level role — `RoleGuard` runs first and hard-denies with no shadow mode, so `/api/users` is gated without an RBAC scope), and `@AuthenticatedOnly()` (no RBAC scope applies, but the principal MUST be a human user — `POST /api/me/password` and `GET /api/me`; service principals, i.e. instance and management API keys, are denied, and it is NOT `@Public()`, AuthGuard still runs — note it short-circuits BEFORE scope resolution, so it is the one lane reachable by a principal carrying no `orgId`). Anything else fails closed
- **Principals** (`permission.guard.ts` decision order): org-scoped management API key (`X-Polyant-Key` — decided purely from its own permission set, never via the user authorization service) → **Platform Admin** → per-instance API key (its own agent only) → human user (JWT). Platform Admin is `users.is_platform_admin`, sits above every organization, bypasses all RBAC, and is read from the DB per request — deliberately NOT carried in the JWT so revocation is near-immediate. It is promoted at boot from `PLATFORM_ADMIN_EMAIL` by `organizations/bootstrap.ts`
- **EE seams**: `AuthorizationStrategy` (OSS = `OssStrategy`) and `EntitlementService` (OSS = `OssEntitlementService`, `isAvailable()` always `false`, so `@RequiresFeature()` routes fail closed in OSS builds)
- **Exposed surface**: only `/api/organizations/:orgSlug/members` (list / assign / remove, `org.member:manage`) + the web page `packages/web/src/app/(admin)/organizations/[orgSlug]/members/page.tsx`. The guard authorizes against the caller's *own* org and cannot see the `:orgSlug` path param, so `MembersService` re-resolves the addressed org and rejects a caller from another one — that service is the cross-org isolation choke-point
- **Membership is granted deliberately; SIGN-IN PROVISIONS NOTHING.** `PUT /api/organizations/:orgSlug/members/:userId` (`org.member:manage`) is the only way into an organization, and it writes **both** rows: `organization_memberships` (which the sign-in callback reads to stamp `orgId` into the JWT) and the `role_bindings` row (which `authz.can()` reads for permissions). `assignRole` alone writes only the binding, which is why `MembersService.assign` calls `ensureDefaultMembership` first — a binding without a membership is a member who resolves no scope and is denied everywhere. Sign-in is now a pure LOOKUP: the Auth.js `jwt` callback calls `resolveSignInOrgId` (`lib/org-provisioning.ts`), whose port exposes **one read capability and no writes** (a unit test pins that, so re-adding a write means deleting it on purpose). A user holding no membership signs in fine, gets no `orgId`, and the panel renders `no-organization` with **no action button** — there is no self-service remedy, so offering one would lie. This replaced auto-provisioning, under which a first sign-in created the membership AND the **Owner** binding, so anyone passing the sign-in domain allowlist became an Owner — on a company-domain allowlist, every employee. **Bootstrap:** a platform admin (`PLATFORM_ADMIN_EMAIL` or the initial-admin seed) holds no membership and therefore no `orgId`, so `MembersService.resolveAndAuthorize` exempts platform admins from its org-match check — without that exemption nobody could add the FIRST member and the deployment would be unusable. The exemption grants nothing new: `PermissionGuard` already lets a platform admin past every permission check before that code runs. There is still no email-invitation flow (#144); "invitation" here means an admin creating the user (`POST /api/users`) and then assigning them a role
- **Not implemented yet**: no invitation flow (unimplemented and untracked — #144 is a separate issue about consolidating the sidebar Members page with Settings → Users, not about invitations)
- **Canonical tenant boundaries** ([ADR-0002](docs/adr/0002-canonical-tenant-boundaries.md)): admin panel routes are tenant-scoped in three tiers — workspace-level for agents and their data, org-level for the dashboard/members/audit-logs, deployment-level for settings and skills (which stay flat). The slugs come from `GET /api/me`; the web proxy propagates the workspace slug to the engine, which validates it against the addressed agent.
- **Audit split**: `authz_audit_logs` is EE (authorization read/access — no OSS write path, guarded by a regression test). OSS management-plane mutations go to `management_audit_logs` (see the Management write-audit log entry above)

## Instances Architecture

The project supports multiple AI assistant **instances**, each with its own configuration:

- **Instance = shared assistant configuration**: an instance defines personality, tools, skills, and can serve multiple users. Identified by `instanceId` throughout the codebase (DB columns: `instance_id`)
- **Branded identifiers (`InstanceSlug` vs `InstanceUuid`)**: the two instance identifiers are distinct branded string types in `packages/engine/src/instances/identifiers.ts`. The human-readable `slug` (`instances.slug` — the external contract: API `model` field, URL `:slug`, channel keys, workspace dirs, `conversationId` prefix) is `InstanceSlug`; the `instances.id` UUID and the FK columns referencing it are `InstanceUuid`. Slug-text tables (memories, conversations, knowledge, scheduled_tasks, audit, traces, ai_logs) store the slug → their store functions take `InstanceSlug`; uuid-FK tables (room, prompts, secrets, channels, instance_skills, instance_tools, skill_env, webhooks/event sources + event_backlog) store the UUID → their store functions take `InstanceUuid`. The ONLY sanctioned slug↔UUID conversion is `resolveInstanceId(slug)` / `resolveInstanceSlug(id)` in `resolve-instance-id.ts`. `asInstanceSlug` / `asInstanceUuid` are zero-cost (runtime identity) casts — use them ONLY at trusted boundaries (DB row reads, validated `@Param`, config constants). A plain `string` is not assignable to a brand, so the compiler now prevents the silent "zero rows" mismatch that used to occur when a slug reached a UUID query (or vice versa)
- **DB table `instances`**: metadata (slug, name, description, status, memoryEnabled, langsmithEnabled, authEnabled)
- **OpenAI-compatible API**: exposes instances as models — clients select an instance via the `model` field
- **Config in DB**: prompts, skills, tools, secrets, channels stored in PostgreSQL (filesystem only used for knowledge files)

### Management API (implemented)

- **Prompt management**: `GET/PATCH /api/instances/:slug/prompts`
- **Tool management**: `GET/PATCH /api/instances/:slug/tools`
- **Skill management**: `GET/PATCH /api/instances/:slug/skills` + skill env vars (`GET/PUT/DELETE`)
- **Secrets management**: `GET/PUT/DELETE /api/instances/:slug/secrets`
- **Channels management**: `GET/PUT/DELETE /api/instances/:slug/channels/:type`
- **Conversations**: `GET/DELETE /api/conversations` + messages
- **Memories**: `GET/POST/DELETE /memories`
- **Analytics**: `GET /api/analytics` + `GET /api/instances/:slug/analytics`
- **Global skill library**: `GET/POST/PUT/DELETE /api/skills`
- **Tool catalog**: `GET /api/tools` (read-only registry list)
- **Room**: `GET/PUT/DELETE /api/instances/:slug/room` + event sources CRUD + definitions CRUD + backlog query + activity log
- **Hooks**: `GET/POST/PATCH/DELETE /api/instances/:slug/hooks`
- **Webhooks**: `POST /webhooks/:webhookToken` — external event ingestion with LLM-based matching

## Development Layers (Claude Code)

This project ships with a set of layered Claude Code helpers under `.claude/`:
- **Rules** (`.claude/rules/`): enforced constraints (always loaded). Coding style, security, testing, git workflow, performance, TypeScript conventions.
- **Hooks** (`.claude/hooks/`): automatic enforcement (pre-commit secrets check, post-edit lint, console.log warning).
- **Agents** (`.claude/agents/`): 8 specialized agents (planner, code-reviewer, architect, tdd-guide, security-reviewer, doc-updater, build-error-resolver, refactor-cleaner).
- **Contexts** (`.claude/contexts/`): behavioral modes (dev, review, research).
- **Commands** (`.claude/commands/`): `/plan`, `/tdd`, `/brainstorming`, `/review`, `/verify`, `/security-scan`.
- **Skills** (`.claude/skills/`): project-specific knowledge (backend-architecture, frontend-design-system).
