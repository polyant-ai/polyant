# Polyant v1.1.0

Polyant v1.1.0 opens the runtime to the wider agent ecosystem — an agent can now consume external MCP servers and be consumed over A2A — and turns the multi-tenant authorization work from an opt-in into the way the platform behaves. It is a minor release by version number and a demanding one by upgrade: authorization, the persisted platform-admin role value, and the frontend URL scheme all change.

> **Read [docs/UPGRADING.md](../UPGRADING.md) before starting.** This is not a rolling upgrade, it is forward-only past migration `0071`, and it forces every user to sign in again.

## Highlights

- **MCP client.** An agent can equip tools from external Model Context Protocol servers, configured per agent, with `none` / `static` / OAuth 2.1 auth modes. Credentials are encrypted at rest and never returned by the API, and `MCP_CONNECT_TIMEOUT_MS` bounds the per-server connect so one slow server cannot stall a turn.
- **A2A server.** An agent can be exposed over the Agent2Agent protocol (Agent Card + JSON-RPC), opt-in per agent and off by default.
- **RBAC is enforced unconditionally.** `AUTHZ_ENFORCE` and its shadow mode are gone: an undeclared route or a failed permission check is a 403, and membership is granted deliberately rather than by signing in.
- **Tenant-scoped frontend URLs.** The workspace URL segment is authoritative, admin routes live under it, and navigation is scope-aware.
- **The agent detail page is navigable.** Every section is a sidebar row addressed by `?tab=`, twenty-three destinations became eighteen, and MCP servers, credentials and the per-agent conversation views each have one home.

## Breaking changes

Each of these is listed with its migration and remediation in the [changelog](../../CHANGELOG.md) and, where it needs an operator decision, in the [upgrade guide](../UPGRADING.md).

- RBAC is always enforced; `AUTHZ_ENFORCE` is removed.
- `AUTH_MODE=alb-oidc` is refused at boot — it cannot satisfy enforced RBAC.
- A new user has no organization membership until an administrator grants one.
- The platform-admin role value is `platform_admin`; migration `0071` is forward-only.
- Migration `0072` grants agent-secret and agent-export permissions to the Member role.
- Flat frontend paths and legacy `?tab=` values no longer resolve.
- An empty tool set now means no tools, not every tool — audit agents with no tool rows before upgrading.
- `POSTGRES_SSL` accepts only `true` or `false`, and `false` now really disables TLS.
- `GET /api/tools` requires `ORG_READ`; `GET /v1/models` returns `[]` for a principal with no resolvable organization.

## Upgrading a development installation

1. Back up PostgreSQL — migration `0071` is forward-only.
2. Audit `POSTGRES_SSL` in every environment.
3. Run `npm ci`.
4. Stop the engine. This is not a rolling upgrade: the old and new code must not run against the same schema.
5. Run `npm run db:migrate`, then `npm run build`.
6. Rotate `AUTH_SECRET` — every user has to sign in again — and start the engine.
7. Assign roles: nobody has a membership until an administrator grants one.
8. Smoke-test sign-in, a representative chat, and one agent's configuration end to end.

## Compatibility

Semantic Versioning applies to the documented OpenAI-compatible API, Plugin SDK and manifest, and documented configuration and migration behavior. Internal engine modules and the admin UI are not public SemVer surfaces. Several of the breaking changes above land inside those surfaces — documented configuration (`AUTHZ_ENFORCE`, `AUTH_MODE`, `POSTGRES_SSL`) and the documented API (`GET /api/tools`, `GET /v1/models`) — so plan for it as a major upgrade whatever the version number says.
