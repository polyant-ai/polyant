# Polyant v1.0.1

Polyant v1.0.1 is a patch release. It lets a WhatsApp channel authenticate to Twilio with a revocable API Key instead of the account Auth Token, and it hardens how credential-bearing webhook URLs are logged and answered.

## Highlights

- **Twilio API Key credentials for WhatsApp.** An operator who holds only a revocable API Key (`SK…` plus its secret) can now run a WhatsApp channel. Twilio computes the `X-Twilio-Signature` header from the account Auth Token and publishes no API-Key-keyed equivalent, so a channel in this mode receives inbound messages on a dedicated webhook URL carrying a server-generated secret. The admin panel reveals that URL and can rotate it.
- **A dedicated WhatsApp configuration card.** The channel now has its own card in the admin panel, with a credential-mode selector, the fields for the selected mode, and the webhook URL to paste into the Twilio Console. Channels that use the Auth Token are unchanged, including their existing webhook URL and signature validation.
- **Credential-bearing webhook paths are redacted in logs.** A webhook URL whose path carries a secret is masked before anything is written to a log file. The safeguard covers both the WhatsApp inbound webhook secret and the Room event-source webhook token.
- **No pre-authentication information disclosure on inbound webhooks.** Every WhatsApp webhook request that fails before authentication — unknown agent, unconfigured or disabled channel, wrong credential mode, wrong secret — returns one identical response, so an anonymous caller cannot enumerate agent slugs or learn which credential mode a channel uses.

## Upgrading

No database migration and no new configuration variable. Existing WhatsApp channels keep their exact behaviour with no operator action: a channel configured before this release continues to use its Auth Token and its current webhook URL.

1. Back up PostgreSQL.
2. Run `npm ci`.
3. Run `npm run build`.
4. Restart the services, then smoke-test sign-in and a representative chat.

### Switching an existing channel to API Key mode

Saving the new mode mints the inbound secret and produces a new webhook URL. Inbound messages are **not delivered between that save and the moment the new URL is configured in the Twilio Console** — the previously configured URL stops being accepted immediately. The same applies in reverse (switching back to Auth Token invalidates the secret-bearing URL) and after a rotation. Plan the change for a low-traffic window and update the Twilio Console right after saving.

### Rolling back

A rollback to v1.0.0 is clean only for channels that were never switched to API Key mode. A channel switched to API Key mode stores credentials that v1.0.0 cannot read: its configuration is rejected on the next save and the channel is disabled at start-up. Switch such a channel back to Auth Token mode, and re-enter its Auth Token, before rolling back.

## Compatibility

Semantic Versioning applies to the documented OpenAI-compatible API, Plugin SDK and manifest, and documented configuration and migration behavior. Internal engine modules and the admin UI are not public SemVer surfaces.

This release adds management endpoints and an inbound webhook route; it removes and changes none. Two existing behaviours are tightened: a Twilio Account SID is validated for format when a WhatsApp channel is saved, and channel configuration is stored exactly as its schema validates it, so keys outside the validated shape are no longer persisted.
