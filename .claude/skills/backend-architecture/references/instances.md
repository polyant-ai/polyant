# Instances: identity, secrets, embeddings, export/import

Moved out of `CLAUDE.md` verbatim: the invariants stayed there, this is the reasoning
and the detail behind them. Read the entry in CLAUDE.md first — it says what the rule
IS; this file says why, and what breaks when it is ignored.

- **Embeddings are per-instance, with an INDEPENDENT embedder provider.** The embedder is a dedicated `instances.embedding_provider` column (`openai` | `bedrock`; Anthropic has no embeddings API), chosen **separately from the chat `provider`** — changing the chat LLM never touches embeddings (migration 0052 backfilled `embedding_provider` from the chat provider so existing instances were unaffected). Each instance also has `embedding_dim` (1024 or 1536): OpenAI can emit either, Bedrock Titan v2 is always 1024. `embeddingProviderFor(provider)` survives only as the default at instance creation and for the migration backfill — it is NOT the runtime source of truth. `provider-resolver.ts` resolves the embedder model + credentials from `embedding_provider` (an `openai` embedder needs `openai_api_key` even when chat is bedrock/anthropic; a `bedrock` embedder needs AWS creds even when chat is openai). The admin Settings tab exposes a dedicated **Embedder** select. The `memories` and `knowledge_chunks` tables have two parallel vector columns (`embedding vector(1536)`, `embedding_1024 vector(1024)`) with an XOR check constraint — exactly one is populated per row, decided by `embedding_dim`. `computeMemoryStatus` validates `embedding_provider`/`embedding_dim` compatibility (via `SUPPORTED_DIMS`): a stranded state like bedrock + 1536 reports `canEnable: false` rather than falsely healthy.

- **Changing the embedder provider is destructive — no conversion/migration.** Embeddings produced by different providers live in incompatible vector spaces, and re-embedding existing data is slow, costly, and error-prone. So switching an instance's `embedding_provider` (openai↔bedrock) does NOT convert existing vectors — it **wipes** them. `resetEmbeddingsForProviderSwitch(slug, uuid, newEmbeddingProvider)` (in `embeddings-gateway/embedding-reset.service.ts`) deletes ALL memories and the ENTIRE knowledge base (documents + chunks, raw content included) and realigns `embedding_dim` to the new provider's default, in one transaction. **The deletes are keyed by the instance SLUG** (the `memories`/`knowledge_*` `instance_id` columns store the slug, not the UUID); the `instances` row update is keyed by the UUID. Passing the UUID to the slug-keyed deletes was a bug that left data orphaned while only realigning the dim — the function now takes both identifiers, branded, so the compiler prevents recurrence. Conversations are untouched — only extracted memories are removed, so keyword (FTS) search over raw messages keeps working. The `PATCH /api/instances/:slug` handler detects the switch with `embeddingProviderChanged` (which now compares `embedding_provider`, not the chat provider) and **rejects it with 400 when there is data to lose unless the body carries `confirmWipe: true`** — protecting scripted Management-API callers from silent data loss. The admin UI shows a destructive-confirmation dialog and sends `confirmWipe` after the user accepts; the PATCH response carries the `wiped` counts. The KB raw text survives a switch via **export/import** (below): export before switching, then re-import to re-embed at the new dim. Memories are not recoverable this way (they are LLM-extracted).

- **AI-provider AWS credentials have a dedicated secret namespace, decoupled from tools.** The AWS credentials used by AWS-backed AI services (Bedrock chat, Bedrock embedder, Amazon Transcribe STT) live under `aws_provider_access_key_id` / `aws_provider_secret_access_key` / `aws_provider_region` in `instance_secrets` (see `SECRET_KEYS`). These are intentionally **distinct** from the generic `aws_access_key_id` / `aws_secret_access_key` / `aws_region` keys that tools (e.g. `file-upload`/S3) declare as `requiredSecrets`, so the AI provider and a tool can point at different AWS accounts without sharing one slot. `config-resolver.ts` (chat `apiKeys.bedrock_*` + STT `sttCredentials.aws`), `embeddings-gateway/provider-resolver.ts`, and `memory-status.ts` all read the `aws_provider_*` keys; the region still falls back to `process.env.AWS_REGION` then default `us-east-1`, and to the AWS SDK default provider chain (ECS/EC2/SSO) when no explicit credentials are set. The bearer token `bedrock_api_key` is unchanged and still takes precedence over SigV4. The Settings-tab AWS card renders whenever chat, embedder, **or** STT uses AWS (one shared block). No migration exists — pre-existing instances re-enter these credentials once.

- **Instance (agent) export/import (JSON bundle).** `GET /api/instances/:slug/export` returns a full-config bundle (`export.service.ts` → `export.schema.ts`, envelope `{ version, exportedAt, type: "instance", instance }`); `POST /api/instances/import` (new) and `POST /api/instances/:slug/import` (overwrite) re-create/replace an instance from one (`import.service.ts`). **Format version is `1.1`** — the importer accepts both `"1.0"` and `"1.1"`; every field added after 1.0 is Zod-`.default()`ed so legacy 1.0 bundles still validate. The bundle covers: core metadata + ALL behaviour flags (`memory/knowledge/langsmith/auth/thinking/stateInPrompt/toolResultsInHistory/debug` + `langsmithProject` + `sttProvider`), GDPR opt-out config (six columns), `embeddingProvider`/`embeddingDim`, prompts, skill assignments (with pinned version), manual tools, channels, skill-env, **hooks**, room, event sources + definitions (incl. `action`/`contextPrompt`/`outbound*`), and scheduled tasks. **Secrets are NEVER exported** — only key names (→ `secret_required` warnings); encrypted skill-env values are omitted; **channel config is exported with credential-like keys stripped** (`stripSensitiveKeys`, pattern `/(?:token|secret|password|key|credential)/i`). On import a channel is (re)enabled ONLY if its non-secret config alone passes the channel's Zod schema — so the credential-less `agent` channel round-trips enabled, while telegram/slack/whatsapp import disabled + a `channel_credentials` warning. **`embeddingProvider`/`embeddingDim` are applied on import-NEW only**; import-OVERWRITE leaves them untouched (switching an existing instance's embedder is destructive — gated behind `confirmWipe` on PATCH, out of scope for import). Slug conflicts on import-new auto-rename (`-imported`, `-imported-2`, …). The web Instances page has Export (per-instance) + Import buttons; the bundle is opaque to the frontend (no client-side schema), so format changes need no web change.

- **Knowledge-base export/import (JSON).** `GET /api/instances/:slug/knowledge/export` returns a JSON bundle `{ version, instanceSlug, documents: [{ filename, content, … }] }` (every document with its raw content). `POST /api/instances/:slug/knowledge/import` bulk-creates documents from such a bundle and re-embeds each with the instance's CURRENT embedder. Filename collisions are resolved by appending a progressive suffix (`manuale.txt` → `manuale (1).txt`), never overwriting; the bundle is validated up front (size, non-empty, per-instance cap) so the import is all-or-nothing, and the embedder must be configured before any document is created. The `export` route is declared BEFORE `:docId` so it is not captured as a document id. Web Knowledge tab has Export/Import buttons.

- **Per-instance config**: AI keys, LangSmith, auth, channels, and Tavily are stored per-instance in `instance_secrets`/`instance_channels` tables. Resolved at runtime via `config-resolver.ts` (30s TTL cache). Only infrastructure vars remain in `.env`/`config.ts`
