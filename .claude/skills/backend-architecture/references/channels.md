# Channels: HTTP, agent-to-agent, adapters, opt-out

Moved out of `CLAUDE.md` verbatim: the invariants stayed there, this is the reasoning
and the detail behind them. Read the entry in CLAUDE.md first — it says what the rule
IS; this file says why, and what breaks when it is ignored.

- **Channel adapters are per-instance**: configs stored encrypted in DB, started/stopped dynamically via admin panel or API

- **Channel boot is fire-and-forget**: `channelManager.startAllForInstance()` is NOT awaited at boot — Slack socket mode can hang and block the entire startup sequence (schedulers, room scheduler). Errors are logged, not thrown

- **GDPR opt-out (STOP/START)**: deterministic keyword gate runs at two chokepoints — a pre-LLM inbound gate at the top of `handleMessage`/`handleMessageStream` (short-circuits opted-out contacts; `runOptoutGate` in `packages/engine/src/optout/optout-gate.ts`) and outbound suppression inside `channelManager.sendOutbound`/`sendOutboundTemplate` (blocks proactive sends, coordinator bypasses with `skipOptoutCheck`). Opt-out state persisted per `(instanceId, channelType, channelId)` in `contact_optouts` table (cascade on instance delete, NOT on conversation delete). Config lives as six columns on `instances` (opt-out enabled, stop/resume keywords, closing/resuming messages, prompt-hint enabled). The LLM is never the enforcer; the keyword is injected into the supervisor prompt purely as informational context. Admin endpoints: `GET/POST/DELETE /api/instances/:slug/optouts`. v1 limitation: STOP as a reply to a Room broadcast is not honored. Spec: `docs/superpowers/specs/2026-06-11-gdpr-optout-design.md`

- **The WhatsApp channel authenticates to Twilio in one of two modes** (`authMode` in the channel config, defaulting to `authToken` for configs written before the feature — enforced both by a Zod `preprocess` on the write path and by the WhatsApp-specific readers; the channel-agnostic config readers were deliberately left untouched). `authToken` = the account Auth Token: unchanged behaviour, inbound webhooks validated via `X-Twilio-Signature` on `POST /webhooks/twilio/:slug/whatsapp`. `apiKey` = a revocable API Key (`apiKeySid` + `apiKeySecret`), passed to the Twilio SDK as `Twilio(apiKeySid, apiKeySecret, { accountSid })` because the SDK builds `/Accounts/{AC…}` REST paths from the account SID. Twilio keys webhook signatures on the Auth Token ONLY and publishes no API-Key-keyed variant, so an `apiKey` channel authenticates inbound on a SECOND route, `POST /webhooks/twilio/:slug/whatsapp/:webhookSecret`, where `webhookSecret` is server-minted (`generateToken(32)` — 32 CSPRNG bytes as hex) and compared in constant time over SHA-256 digests (`timingSafeEqual`). **`setChannelConfig` is the chokepoint**: on every write it prunes the credentials of the unused mode, mints `webhookSecret` when a channel first needs one, unconditionally strips any `webhookSecret` passed inside its `config` argument (the only sanctioned way to set one is the out-of-band `rotateWebhookSecretTo` option), and persists the schema-PARSED config — so pasted whitespace is trimmed and any key outside the validated shape is dropped (this also changed Telegram/Slack: their adapters no longer see keys the schema strips). The PUT handler walks the `CHANNEL_CONFIG_KEYS` allowlist rather than the raw request body, and `webhookSecret` is absent from that allowlist so no client can impose one. Every pre-auth failure on either inbound route — unknown slug, unconfigured/disabled channel, adapter not running, a mode mismatch on either route, AND a wrong path secret — answers the **same 404 with one shared message**, so an anonymous caller cannot enumerate slugs or discover a channel's credential mode; only a bad HMAC signature on the `authToken` route still answers 403 (unchanged prior behaviour). A security review found the global exception filter logging `request.url` while `installFileLogger` tees console output to plaintext files, meaning a VALID path secret would reach disk on any 429/404/403 — fixed by `server/filters/redact-webhook-path.ts`, which masks credential-bearing webhook paths (case-insensitive, since Express routes case-insensitively; fail-safe on an unrecognised `/webhooks/...` shape by masking every segment while preserving the segment count for diagnosis) and incidentally closed a pre-existing leak of the Room event-source webhook token on `/webhooks/:token`. Reveal + rotation live at `GET /api/instances/:slug/channels/whatsapp/webhook-url` and `POST .../rotate-webhook-secret`, both behind `CHANNEL_WRITE` (not `CHANNEL_READ` — the secret is bearer-equivalent) with `Cache-Control: no-store`; the PUT response also echoes `webhookUrl` in `apiKey` mode so a mode round-trip cannot silently leave a dead channel. Both minting and rotation write a `secret.write` management-audit row (key only, never the value). **Accepted costs**: `TRUST_PROXY` matters only in `authToken` mode (it exists so the HMAC is computed over the externally-visible URL — in `apiKey` mode the gate is a path segment no forwarded header can influence); the secret rides in the URL path and will therefore appear in reverse-proxy access logs (Twilio messaging webhooks cannot carry custom headers, so a path segment is the only channel available — rotation is the mitigation); and switching a channel's mode — in EITHER direction, `authToken`→`apiKey` or `apiKey`→`authToken` — interrupts inbound until the Twilio Console is updated: `pruneWhatsAppCredentials` destroys the credentials (and, on the return trip, the `webhookSecret`) of the mode being left, so whichever URL is still configured in the Twilio Console immediately 404s until the operator re-pastes the correct signature/secret URL for the new mode; a forgotten-to-propagate rotation has the identical failure mode. Do not treat a mode rollback as the safe direction — it is exactly as disruptive as the original switch. The admin panel renders WhatsApp through a dedicated `whatsapp-channel-card.tsx` (mode selector + conditional credential fields + the webhook-URL panel with copy and rotate), not the generic field-list loop used for Telegram/Slack — the generic renderer cannot express two mutually exclusive credential modes. The card uses the shadcn `Select` (the design system forbids native `<select>`)
