# Tools, hooks, plugins, MCP

Moved out of `CLAUDE.md` verbatim: the invariants stayed there, this is the reasoning
and the detail behind them. Read the entry in CLAUDE.md first — it says what the rule
IS; this file says why, and what breaks when it is ignored.

- **Conversation lifecycle hooks** (`packages/engine/src/hooks/`): per-instance, DB-configured (event → action) pairs run by `runHooks()` at four fixed pipeline points — `conversation_start` (first turn with empty persisted history — abort-safe vs the coordinator's cancel-and-restart), `message_received` (pre-LLM), `response_generated` (post-LLM, pre-flush), `response_sent` (end of pipeline post; semantics = "handed to channel", NOT delivered). Hooks are observe-only, ALL awaited (sequential, `position` order, per-hook timeout 1–30 s, default 10 s) and log-and-continue — a failing hook never blocks the reply. Action type is `function`: a **hook function** authored via `defineHook(...)` from `@polyant-ai/plugin-sdk` (v1.2.0+), default-exported from a `*.hook.ts` file and discovered at boot by `loadAllHooks()` into `getHookRegistry()` (parallel to the tool loader; plugin `hooksDir`, default `hooks/`). A hook function is NOT a tool — it is never LLM-invoked and never appears in the Tools catalog. Its `handler(ctx)` receives a purpose-fit `HookContext` (built in `hook-context.ts`): `event`, server-built `payload`, `conversation` (read-only `ConversationHistoryApi`), `state` (the conversation store, READ+WRITE — pre-event writes are visible to the supervisor the same turn and ride the commit-on-success flush), scoped `secrets`, `instance.{provider,model,flags}`, and `ai.chat(...)` (an LLM accessor bound to the instance's configured model via the ai-gateway). The handler returns `void` OR a typed control object — `{ halt?, replaceResponse?, regenerate?, injectContext? }` — mapped by `functionActionExecutor` onto the run. (The legacy `tool` action type + `{{path}}` arg-templating + the `HOOK_HALT_KEY` result-key convention were removed in the function cutover; migration `0060_remove_tool_hooks` deletes stale `action_type='tool'` rows.) Hooks bypass `instance_tools` enablement (deterministic admin config, like harness tools), skip only auto-tasks (the `scheduled`/`agent` synthetic channels now DO run the full hook lifecycle on the conversational path; `room`/webhook are supervise-direct and wire only the pre-LLM `message_received` hook in their engines), and audit outcome only (never rendered args — PII). Every execution is ALSO recorded fire-and-forget in `hook_executions` (slug-keyed telemetry, `hook_id` intentionally not a FK; dropped by the deleteConversation cascade, preserved on instance delete like other telemetry) INCLUDING rendered args + truncated result (same exposure class as message `steps`; the global audit log stays outcome-only), exposed via `GET /api/conversations/:id/hooks` and rendered as expandable pills (input/output on click, shared `HookExecutionPill` component) in the conversation-detail timeline (a `message_received` pill legitimately precedes its user message row — that row is persisted commit-on-success at end of turn). `runHooks()` also returns `HookExecutionSummary[]`, threaded onto `StreamOutgoingMessage` so the typed SSE endpoint emits live `hook-execution` events (pre hooks after stream open, post hooks before `done` — which therefore awaits the synchronous post phase); the playground renders them on the assistant turn. Extensible via `action_type` + executor registry in `hook-runner.ts`. Managed via `GET/POST/PATCH/DELETE /api/instances/:slug/hooks` + web "Hooks" tab. **Hook control return** (`HookResult`, `void` = observe-only): (1) `halt: { message, persist? }` — pre-LLM only (`message_received` everywhere, `conversation_start` on the conversational path): skips the LLM and delivers `message` as the assistant reply, persisted like an LLM turn; the runner stops at the first halt; wired via `runPipelinePre` → `shortCircuit` in `handleMessage`/`handleMessageStream` plus the supervise-direct Room + Webhook engines. `persist: false` (SDK v1.5.0+) makes the halted turn **ephemeral**: `runPipelinePost` skips the `pipeline_traces` row, BOTH `stateBuffer.flush()` calls, `afterResponse` (user/assistant rows, summary, memory, debug payload) and the contextPrompt clear — while still running `response_generated`/`response_sent` and writing the `hook_executions` row (the execution happened; only the turn didn't). Absent ⇒ persisted, as before. Honored on the conversational path only — Room/Webhook never call `runPipelinePost`, so they ignore it. (2) `replaceResponse: { message }` — `response_generated` only: replaces the LLM reply before delivery; honored only when the hook declares `mutatesResponse: true`, which makes the engine run that turn **non-streamed** (declare-and-buffer: `hasResponseMutatingHook` → `handleMessageStream` routes through the buffered `runBufferedTurn`), so the replacement is never too late; a `replaceResponse` without `mutatesResponse` on a streamed turn is warned, not silently dropped. (3) `injectContext: string` — pre-LLM only: appended as a system message to the turn's LLM input. (4) `regenerate: { reason? }` — `response_generated` only: discards the LLM output and REPLAYS the whole supervisor turn (system prompt + tools), driven by `generateWithReplay` in `hooks/response-replay.ts`. **HARD-gated on `mutatesResponse: true`** — because replay costs up to 6× a normal turn, an undeclared `regenerate` is DROPPED (warn), not honored, unlike `replaceResponse` (a cheap text swap still applied warn-only on non-streamed turns). The hook owns the stop condition via `payload.response.regenerationCount` (0 on the first pass); the engine only enforces a hard cap `MAX_REGENERATIONS = 5`. `regenerate` WINS over `replaceResponse` in a pass: a same-pass `replace` applies only on a pass where nobody asked to regenerate, and when the loop exits with `regenerate` still set (cap hit / aborted) the raw last output ships — never a superseded `replace`. Extracted seam: `runResponseGeneratedHooks` runs the post-LLM hooks in the loop (abort-safe — it skips the hooks entirely once the signal is aborted, since it now runs BEFORE `runPipelinePost`'s abort gate), then `runPipelinePost` is called with `responseGenerated` so it neither re-runs those hooks nor re-applies replace — one persisted turn. Spend (tokens/cost/latency) is SUMMED across all replay passes into the single `pipeline_traces` row via `addPassSpend` (each pass still logs to `ai_logs` independently); content fields (steps/tools/reasoning/model) are the delivered pass. Wired ONLY into the buffered conversational path (`runBufferedTurn`, which `mutatesResponse` already forces non-streamed); room/webhook run `response_generated` for `replaceResponse` but have no replay loop (they pass `regenerationCount: 0`). **CAVEAT: replay re-executes the whole turn, tools included** — a non-idempotent tool can fire up to 6× and the per-conversation `stateBuffer` accumulates writes across discarded passes, so enable a `regenerate` hook ONLY where the turn is side-effect-free or its tools are idempotent; deterministic (`temperature:0`) turns reproduce identical output and just burn the cap (regenerate suits sporadic output corruption, not systematic errors). Hook-authored replies (halt or replace) persist `metadata: { source: "hook", hookName }` on the assistant row (`hookProvenance`) so the web can badge them. The halt/replace/inject contract types live in `@polyant-ai/plugin-sdk` (`HookResult`/`HookContext`/`HookSpec`). A read-only catalog is at `GET /api/hook-functions`. **First-party hook functions** live in `packages/engine/src/hooks/functions/` (scanned by `getCoreHooksDir()`); the first one is **`conversation-reset`**: on a message that is exactly `RESET` (trimmed, case-insensitive, whole message — same deterministic-keyword shape as the GDPR opt-out gate) it renames the current conversation to `<conversationId>#<5 random digits>` via `conversationStore.renameConversation` (which moves messages, ai_logs, traces, audit, hook_executions, memories AND `conversation_state`), then halts with `persist: false`. Effect: the old conversation stays browsable in the panel under the suffixed id, the next inbound message re-creates the canonical id EMPTY, and the RESET exchange itself lands in neither. Purpose: a conversation id is `${slug}:${channel}:${channelId}`, so colleagues testing an agent from one WhatsApp number otherwise share one ever-growing conversation. Enable it per instance from the Hooks tab (test agents only — the keyword is hardcoded, not configurable). Caveat: the `MessageCoordinator` concatenates a fragment burst, so `RESET` followed immediately by more text arrives as one message and does NOT match. Design: `docs/superpowers/specs/2026-06-10-hook-system-design.md` + `docs/superpowers/specs/2026-07-02-hook-halt-and-respond-design.md` + `docs/superpowers/specs/2026-07-03-hook-functions-design.md` (the tool→function replacement; plan: `docs/superpowers/plans/2026-07-03-hook-functions-engine.md`) + `docs/superpowers/specs/2026-07-23-hook-regenerate-replay-design.md` (the `regenerate`/replay control return; plan: `docs/superpowers/plans/2026-07-23-hook-regenerate-replay.md`) + `docs/superpowers/specs/2026-07-29-conversation-reset-keyword-design.md` (`halt.persist` + the `conversation-reset` hook; plan: `docs/superpowers/plans/2026-07-29-conversation-reset-keyword.md`)

- **MCP client (consume external MCP servers)**: an instance connects to external **remote** Model Context Protocol servers (HTTP/SSE only — no stdio/subprocess) and exposes their tools to the supervisor as native, namespaced tools. Config lives per-instance in the `instance_mcp_servers` table (uuid-FK, mirrors `instance_channels`; encrypted `config` blob), managed via `GET/PUT/DELETE /api/instances/:slug/mcp-servers` + `POST .../test` (`mcp-servers.controller.ts`) and the web **MCP** tab. **Library:** `@ai-sdk/mcp@^1.0` (`createMCPClient`/`auth`) — pin to the **1.x** line: `ai@6`'s `@ai-sdk/provider@3.x` matches 1.x; `@ai-sdk/mcp@2.x` pulls provider@4 and breaks typecheck (same gotcha as `@ai-sdk/openai-compatible`). **Runtime:** `buildMcpTools()` (`agents/tools/mcp/mcp-tools.ts`) runs in `prepareSupervisor` — per enabled server it opens a client (per-turn), calls `client.tools()`, filters by an optional `allowList`, and namespaces each tool `mcp:<slug>:<tool>` → `toModelToolName()` → `mcp__<slug>__<tool>` (same synthesis pattern as the `agent:{slug}` block; core tools win any name collision). Clients are closed at turn end — a `close` handle threaded through `SupervisorContext.mcpClose`, run in `supervise`'s `finally` and on `superviseStream`'s `completed.finally`, plus close-on-throw guards around `prepareSupervisor`/`chatStream` so an open client never leaks. A dead server is log-and-continue (never blocks the turn). **Auth — two modes (`authMode` column):** `static` = bearer/custom-header token in the encrypted `config`; `oauth` = **MCP-native OAuth 2.1** (server-metadata discovery + dynamic client registration + PKCE), driven by `@ai-sdk/mcp`'s `auth()` — the engine implements only a vault-backed `OAuthClientProvider` (`mcp-oauth-provider.ts`): access/refresh **tokens + PKCE verifier live per-conversation in `principal_secrets`** (keys `mcp_<slug>_tokens`/`_verifier`), the **DCR client registration lives per-(instance,server) in `config.dcrClient`** (reused across conversations; `authorizationServerInformation`/`saveAuthorizationServerInformation` back `config.authServerInfo` so the SDK's authz-info caching never spuriously promotes a `staticClient` to `dcrClient`), and the **state→context nonce** rides the reused `oauth_states` table tagged `mcp:<slug>`. When an oauth server has no token yet, `buildMcpTools` catches the SDK's `UnauthorizedError` and synthesizes a single `mcp__<slug>__connect` tool that returns the authorize link (`{ status:"action_required", url }`); the callback `GET /mcp/oauth/callback` (`mcp-oauth-callback.controller.ts`, a near-clone of `oauth-callback.controller.ts`) consumes the single-use state, runs `auth()` to exchange the code, and the SDK `saveTokens` into the vault — next turn the real tools appear. **Caveat:** rooms/webhooks regenerate `conversationId` per run, so per-conversation tokens don't persist there → oauth servers are skipped on those supervise-direct paths (a per-principal token scope is the follow-up); static-auth servers work everywhere. **Security:** admin-supplied url only, validated `https`/rejects private+loopback+link-local hosts incl. bracketed IPv6 (`mcp-url-guard.ts`); MCP secrets are NESTED, so responses/exports use the shared `MCP_SECRET_PATHS` (`mcp-config-mask.ts`) — `maskMcpConfig` redacts `auth.token`/`staticClient.clientSecret`/`dcrClient.client_secret` to `••••` in API responses (`mergeMaskedMcpSecrets` preserves an unchanged secret on edit), and export strips those leaves + drops the whole `dcrClient` (carries `registration_access_token`); write/delete audit via `ManagementAuditAction.McpServer*`. Export/import bundle bumped to **v1.2** (`mcpServers[]`; static servers import disabled until creds re-entered, oauth import enabled, unknown `authMode` skipped). MCP tools **bypass** `instance_tools` (like harness/`agent:` tools). Design: `docs/superpowers/specs/2026-07-20-mcp-client-support-design.md`; plan: `docs/superpowers/plans/2026-07-23-mcp-client-support-engine.md`

- **Plugin system**: external git repos of `*.tool.ts` files authored against `@polyant-ai/plugin-sdk` (a stateless, versioned public contract — git dependency `git+https://github.com/polyant-ai/polyant-sdk.git#v1.0.0`, its own repo `github.com/polyant-ai/polyant-sdk`). The loader scans N roots unioned + de-duped by manifest `name`: `PLUGIN_DIRS` (comma-separated absolute paths, `config.plugins.dirs`, env wins de-dup) ∪ the convention dir `packages/engine/src/plugins/*` (gitignored runtime drop dir). Each root carries a `plugin.json` (`name`, `version`, `engine` semver range, `toolsDir` default `tools`, `namespace` default `name`); every tool loads as `<namespace>:<name>`. A plugin whose `engine` range excludes the running engine version is **skipped with a warning** (boot continues); duplicate final names fail the boot loudly. Discovery/naming/enablement flow through the same `loadAllTools()` → registry → `instance_tools` pipeline as core tools — no DB or API changes. **Module-resolution rule**: a plugin file resolves its imports from its **realpath**, so a plugin must be either a **real dir in-tree** (`src/plugins/<name>`, resolves the monorepo's `node_modules`, `tsx watch` hot-reloads) or an **out-of-tree dir with its OWN `node_modules`** (`npm install` there with the SDK as a git dep, point at it via `PLUGIN_DIRS`, no hot-reload). **Never a symlink** — `tsx` resolves the symlink's realpath (the external repo) and can't find the monorepo deps. The serialized-data boundary is exactly what lets the engine and each plugin resolve their **own** copies of the SDK/`zod`/`ai` without breakage. See [docs/plugins.md](docs/plugins.md), the `plugin-authoring` skill, and the design record at `docs/superpowers/specs/2026-07-02-serialized-plugin-mechanism.md`

- **Tool registry**: tools are authored as `export default defineTool(...)` (from `@polyant-ai/plugin-sdk`) in `*.tool.ts` files under `packages/engine/src/agents/tools/`. `defineTool` serializes the static Zod `parameters` to **JSON Schema at module load, in the tool's own realm** — the only things crossing the tool↔engine boundary are **data** (`inputSchema`) and a **function** (`execute(input, ctx)`), never a live Zod object or a shared singleton. The engine-owned loader (`loadAllTools()`) collects the default export into the registry Map (`registry.ts` is its only writer); `buildTool()` turns a definition into a Vercel AI SDK `Tool`. The supervisor queries `getToolRegistry()` — no hardcoded tool imports. Per-instance enablement stored in `instance_tools` table (auto-recomputed when skills change). Legacy path: `registerTool({ create })` (Zod-object self-registration) still loads (dispatch on `inputSchema`) so migration is incremental

- **Harness tools bypass instance_tools**: tools with `harness: true` are not in the `instance_tools` table. They are injected by the engine when `includeHarness` matches their category (e.g. `"room"`). The supervisor's `buildTools` skips the enabledNames gate for harness tools
